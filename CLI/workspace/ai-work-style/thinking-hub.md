## 1. Core Thesis（核となる主張）

**AIは仕事を奪う「脅威」ではなく、仕事の質を引き上げる「相棒」である。AIを使いこなすカギは、高度な技術知識ではなく「AIとの付き合い方」という仕事術にある。**

補足: 本書の主張は「AIツールの操作マニュアル」ではない。「AIを相棒にすると、あなたの仕事の"つらい部分"が減り、"楽しい部分"が増える」という体験を、田中さんの成長物語を通じて読者に追体験させることが目的である。

## 3. 読者の「具体的な痛み」トップ5

### 痛み1: 「ChatGPTに何を聞けばいいか分からない」問題
- AIツールのアカウントは作った。チャット画面を開いた。でも「何でも聞いて」と言われると逆に固まる。結局Google検索に戻ってしまう。「使いこなしている人」と「触っただけの人」の間に、越えられない壁を感じている

### 痛み2: 「AIの出力をどこまで信じていいのか分からない」問題
- ChatGPTが生成したコードをそのままコミットしていいのか。ドキュメントにAIが書いた文章をそのまま載せていいのか。ハルシネーション（嘘の回答）が怖い。結局、AI出力を一から確認するなら自分で書いた方が早い、というループに陥る

### 痛み3: 「周りはどんどん使いこなしているのに自分だけ取り残されている」焦り
- SNSでは「AIで生産性10倍」「Copilotなしではコード書けない」という投稿が流れてくる。社内のAI活用勉強会に出ても、すでに使いこなしている人の話が前提になっていてついていけない。この焦りがストレスになっている

### 痛み4: 「AIに頼りすぎると自分のスキルが劣化するのでは」という恐怖
- AIにコードを書かせたら、自分のプログラミング力は落ちるのでは。AIに文章を任せたら、自分の文章力が衰えるのでは。「便利なツール」と「依存」の境界線が分からない。電卓で暗算力が落ちたように、AIで思考力が落ちるのではないかという不安

### 痛み5: 「ツールが多すぎて、何から始めればいいか分からない」混乱
- ChatGPT、Claude、Copilot、Gemini、Perplexity、Cursor、Cowork...。毎月新しいAIツールやサービスが出てくる。それぞれの違いも分からない。有料プランに課金すべきかも判断できない。情報収集だけで疲弊している

## 4. タイトル・サブタイトル候補（5案）

### 案1（推奨）
- **タイトル:** AIは「相棒」にするとうまくいく
- **サブタイトル:** ChatGPT・Claude・Copilotに戸惑うエンジニアのための仕事革命物語
- **選定理由:** 「相棒」というキーワードで親しみやすさと安心感を演出。「戸惑う」で読者の共感を得る

### 案2
- **タイトル:** もう怖くないAI時代の働き方
- **サブタイトル:** 現役エンジニアが実践する「AIとの付き合い方」入門物語
- **選定理由:** 不安に寄り添うアプローチ。「怖くない」で心理的ハードルを下げる

### 案3
- **タイトル:** AIを味方につけたエンジニアの仕事術
- **サブタイトル:** ChatGPTもCopilotも「使い方」より「付き合い方」で決まる
- **選定理由:** 「味方」「付き合い方」で人間関係のメタファーを使い、技術書感を排除

### 案4
- **タイトル:** 「AIが怖い」がなくなる本
- **サブタイトル:** 挫折エンジニアがChatGPT・Claude・Copilotの「相棒力」に目覚めるまで
- **選定理由:** ネガティブ感情の直球表現で共感を得る。「相棒力」は造語でフック

### 案5
- **タイトル:** エンジニアのためのAI仕事革命
- **サブタイトル:** 「使いこなせない」から「手放せない」に変わる8つのステップ物語
- **選定理由:** 具体的な数字（8つ）とビフォーアフター構造。章数と一致させることで期待値をコントロール

### 第1章: AIが怖い - 「使えない自分」への焦りと向き合う

**田中さんの課題:**
部長から「チーム全体でAI活用を推進してほしい」と指名される。しかし自分自身がChatGPTを数回触って「微妙だな」と放置した状態。同期の木村がAIを使いこなして上司に褒められているのを目にし、焦りと劣等感に襲われる。

**学ぶ内容:**
1. 「AIが使えない」のは能力の問題ではなく「付き合い方」の問題
2. AIツールの全体像を「3つの役割」で整理する（相談相手・作業アシスタント・情報整理係）
3. 「まず30秒」ルール -- 完璧に使おうとせず、まず1回だけ試す習慣
4. AIへの「期待値」を正しく設定する（100点ではなく60点のドラフトを出すもの）

**ストーリーライン（200字）:**
朝会で部長から「AI活用推進」を任された田中。やる気はあるが、何から始めればいいか分からない。昼休みに同期の木村がChatGPTで仕様書のたたき台を作っている場面を目撃し、衝撃を受ける。帰り道にたまたま佐藤先輩と遭遇。悩みを打ち明けると「私も最初はそうだったよ」と共感してもらい、「まず30秒だけ試してみて」とアドバイスを受ける。翌朝、田中は恐る恐るChatGPTに「Javaのエラーメッセージの意味を教えて」と聞いてみる。

**実践ワーク:**
- [ ] 今日の業務で「ちょっと面倒だな」と感じたことを1つ、AIに聞いてみる（30秒ルール）
- [ ] ChatGPT / Claude / Copilot のうち、1つのアカウントを作成（未作成の場合）
- [ ] 「AIに聞いてみたこと」と「結果どうだったか」をメモに1行書く

### 第2章: まず「聞いてみる」 - AIへの質問力を磨く

**田中さんの課題:**
第1章で恐る恐るAIを使い始めた田中。しかし「何を聞けばいいか分からない」「聞いてみたけどトンチンカンな回答が返ってきた」という壁にぶつかる。「やっぱり自分で調べた方が早い」と思いかける。

**学ぶ内容:**
1. AIへの質問は「Google検索」とは違う -- 「対話」として捉える
2. 良い質問の3要素: 背景（Context）+ やりたいこと（Goal）+ 制約（Constraint）
3. 「曖昧に聞くと曖昧に返る」法則 -- 具体例で体感する
4. 「ダメな回答」が返ってきたときの対処法（追加質問・言い換え・例を示す）
5. プロンプトの「型」を3つだけ覚える（質問型・依頼型・壁打ち型）

**ストーリーライン（200字）:**
ChatGPTに「Javaのベストプラクティスを教えて」と聞いた田中。返ってきたのは教科書的な一般論。「これなら公式ドキュメントを読めばいい」と落胆する。佐藤先輩に相談すると「それ、Google検索と同じ聞き方してない？」と指摘される。佐藤先輩が目の前で「こう聞くんだよ」とデモ。背景・目的・制約を添えた質問をすると、驚くほど具体的な回答が返ってきた。田中は「聞き方で結果がこんなに変わるのか」と目を丸くする。

**実践ワーク:**
- [ ] 同じ質問を「曖昧バージョン」と「具体的バージョン」でAIに投げ、回答の違いを比較する
- [ ] 自分の業務で「よくやる作業」を1つ選び、背景+目的+制約をセットにした質問文を作る
- [ ] AIの回答が「イマイチ」だった場合に、追加質問で精度を上げる体験をする

### 第3章: 日報・メール・資料が30分で終わる - ドキュメント作成のAI活用

**田中さんの課題:**
毎日の日報、週次報告メール、設計書、会議議事録...ドキュメント業務に毎日1.5時間以上かけている田中。「書く作業」が本来やりたい「考える作業」を圧迫している。

**学ぶ内容:**
1. ドキュメント業務を「考える」と「書く」に分離する思考法
2. AIに下書きを作らせて、自分は「レビュー&仕上げ」に集中するワークフロー
3. 日報・メール・議事録・仕様書、それぞれのプロンプト実例
4. 「AIの文章臭さ」を消すコツ -- 自分の言葉に直すチェックリスト
5. テンプレート化して「毎回の手間」をゼロに近づける

**ストーリーライン（200字）:**
金曜日の夕方。田中はまだ週次報告を書いている。チームメンバーは帰宅済み。「こんなこと毎週やってたら仕事が終わらない」とぼやく。翌週、佐藤先輩が「私の日報の書き方見せようか？」と声をかける。佐藤先輩はSlackのやり取りと作業ログを貼り付けてClaudeに日報を生成させ、要点だけ修正して5分で完了。田中は衝撃を受ける。自分も試してみると、1時間の作業が15分に。「AIが書いた文章をそのまま出していいの？」という不安には佐藤先輩が明確な基準を示す。

**実践ワーク:**
- [ ] 明日の日報（または定型的なドキュメント）をAIに下書きさせてみる
- [ ] 自分が書いた文章とAIの下書きを比較し、「自分らしさ」を加える練習をする
- [ ] よく書くドキュメントのプロンプトテンプレートを1つ作って保存する

### 第4章: コードレビューの「もう1人の目」 - 開発業務でのAI協業

**田中さんの課題:**
後輩のコードレビューに時間がかかっている田中。バグの見落としも増えてきた。一方でCopilotを使っている後輩のコードは「動くけど意図が分からない」ものが増えた。AI生成コードの品質管理という新しい課題が浮上。

**学ぶ内容:**
1. Copilot/ChatGPTを「ペアプログラミングの相手」として使う考え方
2. AIにコードレビューを依頼するプロンプト実例（バグ検出・可読性・セキュリティ）
3. AI生成コードの「信頼レベル」判断基準 -- そのまま使える/要修正/使わない
4. テスト設計・テストコード生成でのAI活用
5. 「AIが書いたコード」をレビューするときのチェックポイント

**ストーリーライン（200字）:**
後輩がCopilotで書いたコードに本番障害が発生。田中はレビューで見抜けなかった自分を責める。佐藤先輩に相談すると「AIで書いたコードは、AIでレビューもできるよ」と意外な回答。佐藤先輩はChatGPTにコードを貼り付けて「セキュリティリスクと潜在バグを指摘して」と依頼。人間が見落としやすいポイントが次々と指摘される。田中は「AIをコードレビューの"もう1人の目"として使えばいいのか」と気づく。ただし「AIの指摘を鵜呑みにしない」判断力の大切さも学ぶ。

**実践ワーク:**
- [ ] 最近書いた（または読んだ）コードをAIに貼り付けて、改善点を聞いてみる
- [ ] AIの指摘の中で「的確なもの」「的外れなもの」を仕分けし、判断基準を言語化する
- [ ] テストケースの洗い出しをAIに依頼し、自分が見落としていた観点がないか確認する

### 第5章: 「何から手をつければ…」がなくなる - タスク整理と思考の壁打ち

**田中さんの課題:**
複雑な要件が降ってきたとき、「何から手をつければいいか分からない」状態に陥る田中。頭の中がぐちゃぐちゃで、タスクの優先順位も決められない。設計方針を1人で考え込んで時間を浪費している。

**学ぶ内容:**
1. AIを「壁打ち相手」にする技術 -- 1人で考え込まない仕事術
2. 複雑な要件を「分解」してもらうプロンプト例
3. タスクの優先順位付けにAIの視点を借りる方法
4. 設計判断の比較検討（メリット/デメリット表の自動生成）
5. 「考える」と「悩む」の違い -- AIで「悩む時間」を減らす

**ストーリーライン（200字）:**

## 8. Counter Arguments（想定反論と回答）5つ

### 反論1: 「AIの使い方なんて、ネットの記事やYouTubeで十分学べるのでは？」

**回答:**
断片的なTips記事やハウツー動画は溢れている。しかし「自分の業務にどう組み込むか」を体系的に、かつ感情面の壁（不安・焦り・抵抗感）も含めて描いた書籍はほぼない。本書は「使い方」ではなく「付き合い方」を物語として追体験させる。読者は田中さんの失敗と成長を通じて、自分なりの取り入れ方を見つけられる。記事を100本読むより、1冊の物語を読む方が行動につながる。

### 反論2: 「AIの進化が速すぎて、出版時には内容が古くなっているのでは？」

**回答:**
本書は特定ツールの操作マニュアルではない。「AIへの質問力」「壁打ちの技術」「チームへの導入術」「キャリアの考え方」といった"仕事の原則"を扱っている。ツールのUIは変わっても、「背景+目的+制約を伝えると良い回答が返る」という原則は変わらない。むしろAIが進化するほど、この「付き合い方」の重要性は増す。具体的なツール名やプロンプト例は2026年2月時点の最新情報で記載し、「原則は不変、ツールは進化」というスタンスを明示する。

### 反論3: 「物語形式は回りくどい。テクニックだけ端的に教えてほしい」

**回答:**
テクニック集は既に多数存在する（「ChatGPT＆生成AI 最強の仕事術」「ChatGPT & Copilotの教科書」等）。しかし多くの読者は「テクニックは知っているが行動に移せない」状態にある。物語形式は、読者の「感情」（焦り・不安・小さな成功体験）に寄り添い、「自分もやってみよう」という動機を生む。田中さんシリーズの既刊9冊が証明しているように、物語形式には技術書にない「読了率の高さ」と「行動変容力」がある。

### 反論4: 「エンジニア向けなら、もっと技術的に深い内容が必要では？」

**回答:**
本書は意図的に「ライフ・仕事術」として設計している。技術的に深いAI活用（AI駆動開発、プロンプトエンジニアリング、AIエージェント開発）は別の書籍に譲る（著者の次回作候補にも入っている）。本書のターゲットは「AIを"業務全般"に活かしたいエンジニア」であり、コーディングだけでなく、ドキュメント作成・学習・思考整理・チームマネジメントを含む「仕事全体」を扱う。技術者がライフハック本を手に取るきっかけになることを目指す。

### 反論5: 「AIツールの比較表があれば事足りるのでは？」

**回答:**
ツール比較は2026年現在、無数の記事が存在する。しかし読者が本当に知りたいのは「どのツールが良いか」ではなく「自分の業務のどの場面で、どう使えば楽になるのか」である。本書は業務シーン（日報・コードレビュー・設計検討・学習・チーム展開）ごとにAI活用を描く。ツールは手段として登場するが、主役はあくまで「読者の仕事が楽になること」。特定ツールに依存しないので、ツールが変わっても価値が減らない。

### 文体・トーンの指針

- **一人称:** 三人称（「田中は～」）。地の文はですます調ではなく、である調。ただし会話文は自然な話し言葉
- **読者への語りかけ:** 各章末の「やってみよう」コーナーのみ「ですます調」で読者に直接語りかける
- **専門用語:** 初出時に必ず平易な説明を添える。ただし読者はエンジニアなので、プログラミング基本用語（変数、関数、API等）の説明は不要

- **技術的正確性:** プロンプト例やAI出力例は、2026年2月時点のChatGPT-4o/Claude 3.5 Sonnet以上/GitHub Copilotを想定。ただし特定バージョンに依存する記述は避け、普遍的な原則を重視

### 注意事項（絶対に守ること）

1. **技術書にしない:** プロンプトエンジニアリングの体系的解説、API仕様、モデルの仕組みの説明は入れない。あくまで「仕事で使うとこう便利」の実践レベルに留める
2. **特定ツールを推奨しない:** ChatGPT/Claude/Copilotはフラットに扱う。「○○が最強」という記述はNG。読者が自分に合うツールを見つけることを促す
3. **田中さんを「ダメな人」にしない:** 田中さんは「普通のエンジニア」。不器用だが真面目で、最終的にはきちんと成長する。読者が共感し、応援したくなるキャラクターであること
4. **佐藤先輩を「完璧な人」にしない:** 佐藤先輩にも「最初はAIが苦手だった」エピソードを入れる。読者が「自分も佐藤先輩みたいになれる」と思えること
5. **煽らない:** 「AIを使わないと終わる」的な恐怖訴求はしない。「使うともっと楽になるよ」というポジティブなメッセージで統一する
6. **プロンプト例は実用性優先:** 理論的に美しいプロンプトより、「明日から使える」プロンプトを優先する
7. **既刊との整合性:** 田中さんの基本キャラクター（真面目・向上心・不完全）と佐藤先輩の関係性は既刊と矛盾させない。ただし本書は独立して読めること

## 14. 章間接続メモ

各章の接続ポイントを定義し、ストーリーの連続性を確保する。

### 第1章 → 第2章

- **前章ラストの状態:** 田中がChatGPTに初めてJavaのエラーメッセージの意味を聞き、「便利かも」と感じた。AI活用への第一歩を踏み出したが、まだ恐る恐るの段階。
- **経過時間:** 2日後（同じ週の水曜日）
- **次章冒頭の状況:** 第1章の成功体験に気をよくした田中が、もう少し踏み込んだ質問「Javaのベストプラクティスを教えて」をChatGPTに投げるが、一般論しか返らず壁にぶつかる。「最初はうまくいったのに...」というギャップがドラマの起点。

### 第2章 → 第3章

- **前章ラストの状態:** 田中が「質問型・依頼型・壁打ち型」の3つの型をノートにメモし、AIへの質問力の基礎を習得した。「もっと色々な場面で試したい」と前のめりになっている。
- **経過時間:** 3日後（翌週の金曜日）
- **次章冒頭の状況:** 質問力は上がったが、毎日の業務で最も時間を食っているのはドキュメント作成だと気づく。金曜夕方に週次報告を書いている場面から始まり、「質問力を活かして、この"書く作業"を効率化できないか？」という問いが生まれる。

### 第3章 → 第4章

- **前章ラストの状態:** 日報・週次報告・議事録のプロンプトテンプレートを作成し、ドキュメント業務の効率化に成功。浮いた時間で「本来やりたい仕事」に集中できるようになった。
- **経過時間:** 1週間後（翌週の木曜日）
- **次章冒頭の状況:** ドキュメント業務は効率化したが、もうひとつ時間がかかっている業務がある。コードレビューだ。そんな折、後輩がCopilotで書いたコードに本番障害が発生。AIとコーディングの関係に正面から向き合うことになる。

### 第4章 → 第5章

- **前章ラストの状態:** AI生成コードの「信頼レベル」を判断する基準を学び、テスト設計にもAIを活用する成功体験を得た。開発業務でのAI協業に自信がついた。
- **経過時間:** 約1週間後（翌週の水曜日）
- **次章冒頭の状況:** 日常業務でのAI活用は進んだが、新規案件でマイクロサービス化という大型設計を任される。「タスクや質問の粒度が小さい」AIの使い方はできるようになったが、「複雑で曖昧な課題」にAIをどう活用するかが次のテーマ。

### 第5章 → 第6章

- **前章ラストの状態:** 「困ったらまずAIに壁打ち」が習慣になり、設計判断やタスク整理で思考の交通整理にAIを活用できるようになった。
- **経過時間:** 約2週間後（翌月の月曜日）
- **次章冒頭の状況:** 壁打ちで整理した設計方針が承認され、次の案件でReactを使うことが正式に決定。しかしReactは未経験。業務活用ではなく「学習・キャッチアップ」というAI活用の新しい領域に踏み出す。

### 第6章 → 第7章

- **前章ラストの状態:** AIを「パーソナル家庭教師」として活用してReactの基礎を短期間で習得。「情報鮮度の注意点」も学び、AIとの付き合い方がさらに成熟した。
- **経過時間:** 約1ヶ月後
- **次章冒頭の状況:** 個人としてのAI活用は十分に定着。高橋部長からの「チーム全体でAI活用を推進してほしい」という当初の使命に本格的に取り組むフェーズへ。自分が使えるようになることと、チームに広めることは全く別のスキルだと気づく。

### 第7章 → 第8章

- **前章ラストの状態:** チームプロンプトライブラリが誕生し、セキュリティガイドラインも整備。チーム内でAI活用が少しずつ定着し始めた。「使わない人を否定しない」という姿勢も身についた。
- **経過時間:** 約3ヶ月後（物語開始から約半年後）
- **次章冒頭の状況:** 半期評価面談で高橋部長から成果を認められる。チームの残業時間も減少。しかしAIエージェント技術の急速な進化を目の当たりにし、「ここまで来たのに、さらにその先がある」という新たな不安に向き合う。成長の物語のクライマックスへ。

## 15. まえがき・あとがき・付録 設計

### 15-1. まえがき（1,500字想定）

**含むべき要素:**
1. **読者の不安への共感から入る:** 「AIが怖い」「ChatGPTを触ったけど何が便利か分からない」「周りが使いこなしていて焦る」-- そんな気持ちを持っているあなたへ、という入り方
2. **著者自身のAI体験:** 著者もAIに戸惑った経験を正直に語る。田中さんの物語は著者自身の体験がベースであることを示唆し、リアリティを担保する
3. **本書の読み方ガイド:** 物語パート（田中さんのストーリー）→ 解説パート（具体的な使い方）→ 実践パート（やってみようワーク）の3層構造で読めることを説明。「前から順に読んでもいいし、気になる章から読んでもいい」と伝える
4. **「田中さんシリーズ」の簡単な紹介:** 初めて読む人向けに「田中さんシリーズ」のコンセプトを1-2文で紹介。「既刊を読んでいなくても本書は独立して楽しめます」と明記
5. **本書のゴール宣言:** 「読み終えたとき、AIが"脅威"ではなく"相棒"に見えるようになっていること」を約束する

**トーン:** 温かく、語りかけるような「ですます調」。押しつけがましくなく、「一緒に歩みましょう」という姿勢。技術書のまえがきにありがちな硬さを排除する。

**読者への語りかけ方:** 「この本を手に取ってくれたあなたは、きっと○○と感じているのではないでしょうか」という共感型。読者を「遅れている人」としてではなく「これから始める仲間」として迎える。

### 15-2. あとがき（1,500字想定）

**著者メッセージ:**
1. **田中さんの物語を通じて伝えたかったこと:** AIは使い方ではなく「付き合い方」。完璧でなくていい。まず30秒から。-- 本書のキラーフレーズを振り返りながら、著者のメッセージをまとめる
2. **「正解はない」というメッセージ:** AIとの付き合い方に唯一の正解はなく、読者それぞれが自分のペースで見つけていくもの。本書はそのきっかけにすぎない
3. **読者への感謝と応援:** 「最後まで読んでくださりありがとうございます。あなたの仕事が少しでも楽しくなったら、著者としてこれ以上の喜びはありません」

**既刊紹介の仕方:**
- 「田中さんはこの本以外にも、さまざまな技術や仕事術と向き合ってきました」という自然な導入
- 3-4冊をピックアップし、本書との関連を1行ずつ添える:
  - 時間管理本: 「AIで浮いた時間をどう使うか -- 田中さんの時間管理術はこちら」
  - Git/GitHub本: 「Copilotを活用する土台となるGitの基礎は、田中さんのこの本で」
  - Docker本: 「開発環境をAIと一緒に構築するなら、まずDockerの基礎から」
  - 副業本: 「AIスキルを副業に活かしたい方は、田中さんの副業奮闘記もどうぞ」
- Kindle上の著者ページへの誘導リンクを添える

**次回作予告:**
- 「田中さんのAIとの旅はまだ続きます」という含みを持たせる
- 具体的な次回作タイトルは記載せず、「AI駆動開発」「AIエージェント活用」など技術的にもう一段深い領域を匂わせる
- 「次回作の情報はX（旧Twitter）でお知らせします」としてSNSフォローを促す
