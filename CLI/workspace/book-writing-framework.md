# 書籍執筆フレームワーク

> 本ドキュメントは、AI並列執筆で書籍を短期間で仕上げるための再利用可能なフレームワーク。
> 田中さんシリーズ Claude Code本（第5弾）の実績をベースに汎用化したもの。
> シリーズ物・単発物どちらにも対応。

---

## 全体フロー

```
Phase 0:  テーマ検証（出す前に「出すべきか」を問う）
    ↓ GO判断
Phase 1:  thinking-hub作成（← ここが品質の8割を決める）
    ↓
Phase 1R: thinking-hub Claudeレビュー & 修正反映（/review-thinkinghub）
    ↓
Phase 1A: thinking-hub 著者レビュー & 承認（著者が通読し、方向性・設定を最終確認）
    ↓
Phase 2:  初稿の並列執筆（Subagent 5+5+2バッチ）
    ↓
Phase 3:  3視点レビュー（/review-book）
    ↓
Phase 4:  修正反映（/fix-review。技術エラー → 文体 → 改善提案の順）
    ↓
Phase 5:  著者レビュー & 対話的修正（必要に応じて数周）
    ↓
Phase 6:  最終バランスチェック & 完成
```

---

## Phase 0: テーマ検証

フレームワークで最短3日の執筆が可能になった分、「出すべきか」の判断が重要になる。
駄文の量産はブランド毀損につながる。一方、需要は出してみなければわからない面もある。
このPhaseは、最小コストで「書く価値があるか」を見極めるためのフィルター。

### 検証ステップ（所要: 半日〜1日）

**1. 市場の温度感チェック**
- Kindleストアでテーマを検索し、競合書籍の数と評価を確認
- 「競合が多い = 需要がある」「競合がゼロ = 需要がないか、ブルーオーシャン」の見極め
- SNS（X、Zenn、Qiita等）でテーマのキーワードがどれくらい話題になっているか

**2. Core Thesisの壁打ち（Phase 1のStep 2を先行実施）**
- Claudeに候補を出させ、著者が「これは自分が書きたいか？」を問う
- この段階で「別に自分が書かなくてもいいな」と思ったら、そこでやめる
- **「自分だから書ける角度」が見つかるかどうか**が最大の判断基準

**3. GO/NO-GO判断**

| 判断 | 条件 |
|------|------|
| **GO** | Core Thesisに著者自身が納得 + 市場に一定の需要が見える |
| **保留** | テーマは良いがCore Thesisが定まらない → 寝かせてから再検討 |
| **NO-GO** | 著者の熱量が低い / 競合が強すぎて差別化困難 / ニッチすぎる |

> **背景**: フレームワークが品質を担保するのは「構成・文体・一貫性」の領域。
> 「この本に読者の時間を費やす価値があるか」はフレームワークでは担保できない。
> Phase 0はその判断を著者自身が行うための仕組み。

## Phase 1: thinking-hub作成（最重要）

thinking-hubは「この1ファイルだけで、執筆AIチームが全章を書き上げられる」精度を目指す。
並列執筆の品質上限 = thinking-hubの精度。ここが甘いと、後工程でいくらレビューしても矛盾が消えない。

### thinking-hub作成の対話フロー

thinking-hubは著者とClaudeの対話で段階的に作る。
Claudeが得意な「型の展開」と、人間にしかできない「魂の注入」を分離し、各ステップで著者の確認・判断を挟む。

```
Step 1: テーマ入力          ← 著者が「何について書きたいか」を伝える
    ↓
Step 2: Core Thesis 壁打ち   ← Claude が候補生成 → 著者が選択・修正
    ↓                        ※ ここが本の方向性を決める。時間をかけてよい
Step 3: 読者ペルソナ確認     ← Claude が3パターン生成 → 著者が実在の読者像と照合
    ↓
Step 4: 読者の痛み確認       ← Claude が5つ生成 → 著者が優先度を判断
    ↓
Step 5: タイトル候補選定     ← Claude が5案生成 → 著者が選択
    ↓
Step 6: キャラクター設定     ← 著者がシリーズ/単発を判断（後述）
    ↓                        Claude がキャラ案生成 → 著者が成長アーク・口癖を確認
Step 7: 章構成レビュー       ← Claude が全章の課題・ストーリーライン・接続を生成
    ↓                        → 著者が章の順序・スコープ・感情の流れを確認
    ↓                        ※ 用語リストもここで確定させる
Step 8: 残りを一括生成       ← Claude がキラーフレーズ・反論・差別化・市場戦略を生成
    ↓                        → 著者がざっと確認
Step 9: 品質チェック         ← 末尾のチェックリストで最終確認
```

**Claudeだけで埋められるもの** と **著者の判断が必要なもの** の区別：

| ステップ | Claudeの役割 | 著者の役割 |
|---------|-------------|-----------|
| Step 2: Core Thesis | 候補を3-5案生成 | **「これが言いたい」を選ぶ・磨く** |
| Step 3: ペルソナ | パターン生成 | **実在の読者像と照合し、リアリティを担保** |
| Step 4: 痛み | 網羅的に洗い出し | **優先度と「刺さる順」を判断** |
| Step 5: タイトル | 候補生成 | **最終選定** |
| Step 6: キャラクター | 設定案・口癖候補 | **成長アークの方向性を決定** |
| Step 7: 章構成 | 構造・接続の設計 | **スコープ・順序・感情の流れを承認** |
| Step 8: その他 | ほぼ自動生成 | ざっと確認 |

> **ポイント**: Step 2（Core Thesis）と Step 7（章構成）は特に時間をかける。
> Claude Code本では、佐藤先輩の会話（本のテーゼ）を何往復も壁打ちして
> 「構造を立体的に見る力」にたどり着いた。最初から正解が出ることは稀。

### キャラクター設定の分岐

| パターン | キャラクター設定の方法 | 入力物 |
|---------|---------------------|--------|
| **シリーズ物**（田中さんシリーズ等） | `shared-characters.md` を参照し、thinking-hubには本書固有の追加設定のみ記載 | shared-characters.md + thinking-hub |
| **単発・別シリーズ** | キャラクター設定をthinking-hub内に完結させる（共通ファイルへの依存なし） | thinking-hubのみ |

シリーズ物の場合、shared-characters.md に定義されている情報（年齢、性格、口癖、基本設定）は
thinking-hubに重複記載しない。thinking-hubには以下だけ書く：
- **本書固有の悩み**（この本でのみ直面する課題）
- **本書固有のキャラクター**（この本だけに登場する人物）
- **成長アーク**（この本での変化の軌跡）

### thinking-hubに必須の16セクション

（2026-07改訂: 運用実態に合わせて10→16へ拡張。雛形は `CLI/templates/book-contents-think/thinking-hub.md`、実例は `CLI/workspace/kiro-cli/thinking-hub.md`）

| # | セクション | 内容 | なぜ必要か |
|---|-----------|------|-----------|
| 1 | **Core Thesis** | 本書の核となる主張を1-2段落で | 全章のトーンと方向性を揃える錨 |
| 2 | **ターゲット読者ペルソナ** | 3パターン程度。職種・技術スタック・悩み・本を見つける瞬間まで | 「誰に向けて書くか」がブレると文体がブレる |
| 3 | **読者の痛みトップ5** | 読者が抱える具体的な課題 | 各章が必ずいずれかの痛みに対応する構造を作る |
| 4 | **タイトル・サブタイトル** | 候補と選定理由 | 書名が決まると全体のトーンが固まる |
| 5 | **キャラクター設定** | 主人公の成長アーク・口癖・本書固有の悩み。メンター・サブキャラも同様 | 並列執筆でキャラがブレる最大の原因は設定の曖昧さ |
| 6 | **章構成（各章の詳細）** | 章ごとに「課題・学ぶ内容・ストーリーライン・実践ワーク」を記載 | **並列執筆の設計図。ここの解像度が矛盾の発生率を直接決める** |
| 7 | **キラーフレーズ候補** | 10個程度。読者の記憶に残るフレーズ | 各章にフレーズを散りばめることで印象に残る本になる |
| 8 | **想定反論と回答** | 5つ程度 | 本文中で先回りして反論に答えるための材料 |
| 9 | **差別化ポイント** | 競合書籍との比較 | 「この本にしかない価値」を全章で意識して書ける |
| 10 | **市場戦略** | 価格・カテゴリ・文字数目安・クロスセル | 分量感と読者導線の指針 |
| 11 | **各章シーン分解** | 章ごとのシーンを詳細型で（CLAUDE.mdの粒度要件: 5項目・各章4〜6シーン） | 並列執筆の実質的な台本。ここが薄いと章内の展開がAI任せになる |
| 12 | **各章感情アーク** | 章ごとの感情の起点→終点 | 成長の飛躍・感情の不連続を設計段階で防ぐ |
| 13 | **キャラクター台詞サンプル集** | 主要キャラごとの口調見本 | 並列執筆時の口調ブレを防ぐ実物見本 |
| 14 | **章間接続メモ** | 前章ラスト→経過時間→次章冒頭 | 時間軸矛盾・接続切れの防止（check-consistencyの照合元） |
| 15 | **まえがき・あとがき設計** | 導入と締めの設計 | 本文と同時に設計しないと後付け感が出る |
| 16 | **付録: 執筆チーム向け指示事項** | バッチ分割・命名・レビュー観点・禁止事項 | Subagent並列執筆（5+5+2）への直接の指示書 |

### 章構成の書き方（Phase 1で最も重要な部分）

各章に以下を必ず定義する。これが並列執筆の「契約」になる。

```markdown
### 第N章: [タイトル]

**主人公の課題:** （この章で何に直面するか）
**学ぶ内容:** （番号付きリスト。具体的な技術トピック）
**ストーリーライン:** （起承転結を含む段落。感情の動きも記述）
**実践ワーク:** （読者向けチェックリスト）
```

### 章構成で明示すべき「接続情報」

並列執筆で矛盾を防ぐために、以下を章構成の中に埋め込む：

- **時間軸**: 各章がいつの出来事か（1週目、1ヶ月後、半年後など）
- **前章からの接続**: 前章の次回予告と、この章の冒頭がどう繋がるか
- **キャラクターの状態**: この章時点での主人公のスキルレベル・心理状態
- **用語リスト**: 本書で統一すべき技術用語・クラス名・プロジェクト名

> **実績からの教訓**: Claude Code本では用語リストを明示しなかったため、
> 「Worklog vs TimeEntry」「Swarm vs マルチエージェント」の不統一が発生した。
> 用語リストはthinking-hubに必ず含めること。

### 共通フォーマットの定義

章の構成テンプレートもthinking-hubに含める（例: 田中さんシリーズの場合）：

```
1. 冒頭引用（主人公の内心独白）
2. シーン（セクション番号付き: N.1, N.2...）
3. 技術解説ボックス
4. コラム（1章に1つ程度）
5. 振り返り
6. やってみよう（チェックボックス形式）
7. 次回予告
```

## Phase 2: 初稿の並列執筆

### 入力物
- thinking-hub.md（Phase 1で作成）
- shared-characters.md（シリーズ物の場合のみ。単発の場合はthinking-hub内にキャラ設定が完結）
- 既刊書籍のepubファイル（文体のスタイル参照用。新シリーズの場合はトーン指示で代替）

### 実行方法
- Subagentで並列執筆。**5+5+2のバッチ分割**が安定（12章の場合）
- 各Subagentにthinking-hub.md + shared-characters.md + スタイル参照を渡す
- 1章あたりの目安: 6,500〜9,500字（コードブロック含む）

### なぜ並列でも品質が保てるか
- 全Subagentが同じthinking-hub.mdを読んでから書き始める
- 章ごとの「課題・ストーリーライン・接続情報」が明確なので、各章の境界が自然と揃う
- 文体はスタイル参照（既刊epub）で統一される

## Phase 3: 3視点レビュー

初稿完成後、以下の3視点で並列レビューを実行する。

| 視点 | チェック観点 |
|------|------------|
| **編集者** | 文体統一・構成・キャラクター一貫性・感情アーク・章間接続 |
| **シニアエンジニア** | 技術的正確性・コマンド動作検証・公式ドキュメントとの照合 |
| **ジュニアエンジニア** | 初心者の理解しやすさ・再現可能性・「置いていかれそう」ポイント |

- レビュー結果は `review-items.md` に一覧化（指摘番号・優先度・対象箇所・内容・ステータス）
- 3視点の組み合わせが網羅性を担保する

---

## Phase 4: 修正反映

レビュー指摘を以下の優先度順に対応する：

1. **技術エラー**（コマンドが動かない、設定が間違っている等）
2. **一貫性の問題**（用語・クラス名・時間軸の矛盾）
3. **文体の問題**（「ですます調」の混在、キャラクターの口癖のブレ等）
4. **改善提案**（構成変更、エピソード追加等）

修正後、全ファイルを通読してバランスチェックを実施する。

---

## Phase 5: 著者レビュー & 対話的修正

著者自身が読み通し、「読んでみての違和感」を指摘する。
このフェーズの指摘は技術的正誤ではなく、**トーン・メッセージ・哲学**の領域になることが多い。

- 選択肢を複数提示 → 著者が方向性を選択 → 具体案を作成、のループ
- 本のテーゼに関わる部分は壁打ちを重ねて深掘りする
- 必要に応じて数周回す

---

## Phase 6: 最終バランスチェック & 完成

全ファイルを並列で読み込み、以下を最終確認：

- [ ] 全章の時間軸に矛盾がないか
- [ ] 前章の次回予告と次章の冒頭が接続しているか
- [ ] キャラクターの口癖・性格が全章で一貫しているか
- [ ] 用語・クラス名が統一されているか
- [ ] 技術コマンド・設定は公式ドキュメントと照合済みか
- [ ] コード例は読者がコピーして動作するか

## 補足: thinking-hubの品質チェックリスト

thinking-hubを書き終えたら、以下を確認してからPhase 2に進む：

- [ ] Core Thesisは1文で要約できるか？
- [ ] 各章の「学ぶ内容」が重複なく全体をカバーしているか？
- [ ] 各章のストーリーラインに感情の動き（不安→気づき→成長）が含まれているか？
- [ ] 章間の接続（次回予告→冒頭）が全ペアで定義されているか？
- [ ] 統一すべき用語のリストがあるか？
- [ ] キャラクターの成長アークが章ごとに段階的か？（一気に成長しすぎていないか）
- [ ] 読者ペルソナの「痛み」と各章の「課題」が対応しているか？
- [ ] **各章に「壁→仕組み→結果」の三幕構造が明示されているか？** 時間経過だけで章を並べていないか。各章の冒頭で課題を提示し、末尾で「仕組みでクリアした」実感を描く構造になっているか
- [ ] **「やってみよう」ワークが章間で重複していないか？** 似たワークが別の章にあれば統合する
- [ ] **専門比喩（IT比喩等）のレベルが適切か？** シーン分解に書く具体例が、コードレベル（while/break等）ではなくコンセプトレベル（技術的負債、デバッグ等）に留まっているか。エンジニア以外の読者が文脈から推測できるか
- [ ] **免責事項の配置が適切か？** 毎章末に入れると煩い。「はじめに」と「おわりに」の2箇所で十分か検討する。ホットライン等の情報が本書のスコープに合っているか
- [ ] **キャラクターの年齢に応じた行動制約を守っているか？** 未成年キャラにノンアルコール飲料を飲ませていないか等、年齢設定と行動の整合性をチェック
- [ ] **シーン間で「初めて」体験が重複していないか？** ある行動の「初体験」シーンが複数章にまたがって存在すると矛盾になる。テイスティング・初飲み会・初断酒日等の「初」を一覧化して重複を排除
- [ ] **環境設計を扱う章は「物理・デジタル・社会」の3軸が均等か？** 物理環境だけ具体的でデジタル・社会が薄い、等の偏りがないか
