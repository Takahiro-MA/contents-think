## 1. 企画概要

### 書籍タイトル（仮）
Codex CLI入門（正式タイトル未定）

### ターゲット読者
- ChatGPTは使っているがCLIコーディングツールは未経験の人
- OpenAIエコシステムに既に課金している人（Plus $20/月）
- AI駆動開発の経験は問わない（未経験者も含む）
- Claude Code本の読者である必要はない

### 著者スタンス
- Claude Code本で確立した「AIと人間が協働してコードを書く」哲学を維持
- ただしCodex本の本文でClaude Codeに依存する説明はしない
- 「同じ哲学を、OpenAIの道具立てで実現するとどうなるか」を誠実に描く

## 2. 差別化方針

### 調査に基づく確定事項

#### 設計思想調査の結論（詳細: research-design-philosophy.md）
- 「Claude Code = ペアプロ / Codex = 自律」の二項対立は成立しない
- 両者ともagent。違いは語彙・ブランディング・デフォルト設計のレベル
- 著者スタンスはブレずに書ける

#### 機能差分調査の結論（詳細: research-feature-diff.md）
- 書くべき具体ネタは十分にある
- 特にTier 1の5つはCC本と完全に別物
- 独立した書籍として成立する材料が揃っている

### 独立完結性の3原則

| 原則 | 内容 |
|------|------|
| **独立完結** | Codex本だけ読んで、ゼロからCodex CLIを使えるようになる |
| **著者の一貫性** | 「AIと人間が協働してコードを書く」哲学は共通だが、Codex本の中で自然に語る（前著を引用しない） |
| **クロスセル** | 「おわりに」や著者紹介で触れる程度。本文の依存はゼロ |

### Claude Codeの扱い方
- 本文の主語はあくまでCodex CLI
- 田中さんの内心で「前に使ったツールとはここが違うな」とたまに思う程度
- 後輩への説明＝読者への説明。後輩がClaude Codeを知らない＝読者が知らなくていい
- 比較が前提の説明はしない

```
○ 「サンドボックスで隔離されるから、安心して試せますよ」（Codex単体で完結する説明）
○ 田中さんの内心：（前のツールではhooksで制御してたけど、こっちはOS層で隔離か…）
× 「Claude Codeではhooksで17イベントを制御しますが、Codexでは…」（比較が前提の説明）
```

### 書籍化すべき差分の優先順位

#### Tier 1：章の柱にすべき差分（必須）
1. **Codex Cloud（CLI経由のクラウド委任）** — CC本に完全未重複
2. **AGENTS.md（オープン標準）** — CLAUDE.mdとは「料理」が違う
3. **sandbox + 承認モードの安全設計** — hooksとは根本的に別アプローチ
4. **codex exec（非対話モード）** — CI/CD特化はCC本にない
5. **CLIからCloud/CIへの接続** — CC本は「同一engine」前提、Codexは「CLIを起点に広がる」

#### Tier 2：章やコラムで厚く扱う差分
6. profiles / TOML設定管理
7. Web検索（cached/live）
8. モデル選択（GPT-5.4 / 5.3-Codex / mini）
9. Codex App + integrated terminal（コラム程度）
10. 並列実行の自動化

#### Tier 3：触れるが深入りしない差分
11. 価格モデル・APIキー統合（導入章で軽く）
12. OSS / Apache-2.0の意味（コラム向き）
13. Skills クロスプラットフォーム互換（AGENTS.mdと合わせて言及）
14. IDE連携の対応表（付録向き）
15. コミュニティ規模（おわりに向き）

### CLI主体の方針
- あくまで「Codex CLI入門」。Desktop Appを章の柱にはしない
- キャプチャを使わない執筆スタイルを維持
- Appはコラムで紹介する程度
- 「CLIが主語。そこからCloud・CI・チーム運用に広がる」構図

## 3. 物語設計

### ストーリーの型
**連作短編（2）× 先輩として導く（5）× 炎上救出（8）** の組み合わせ

```
田中さんが、炎上気味のプロジェクト（or 複数案件）に関わることになる。
後輩と一緒にCodex CLIを使い始め、問題を1つずつ解決していく。
各章が比較的独立したエピソードで、1つの問題を1章で解決する連作短編型。
```

### CC本との物語構造の対比

| 要素 | CC本 | Codex本 |
|------|------|---------|
| 田中さんの立場 | 教わる側（AI初心者） | 先輩エンジニア（AIツールは後輩と一緒に学ぶ） |
| メンター | 佐藤さん（常にそばにいる） | 不在（田中さんがエンジニア経験で後輩を導く） |
| AIツール経験 | なし→佐藤さんに教わる | なし→後輩と一緒に発見していく |
| プロジェクト状況 | 新規開発（ゼロから） | 途中参加（既存コード・炎上案件） |
| 時間軸 | 6ヶ月の成長 | 短期集中 |
| 章の構造 | 前章の続き（直線） | 各章で1つの問題解決（連作） |
| 感情のアーク | 不安→成長→自信 | 混乱→整理→信頼関係構築 |

### 田中さんの立ち位置（重要な設計判断）

**パラレルワールド方針により、田中さんにClaude Code経験は設定しない。**

- 田中さんはバックエンドエンジニア3-5年目。AIコーディングツールは初めて
- Codex CLIが「初めてのAIコーディングツール体験」になる
- 読者と田中さんが完全に同じ目線でCodexを発見していく

これにより：
- 「なぜClaude Codeじゃないの？」という問い自体が消える
- 他のAIツールとの比較を内心で描く必要がなくなる
- 田中さんが素直に感動・戸惑い・発見を表現できる
- ストーリーの制約が大幅に減り、展開の自由度が上がる

### 二重構造の設計

| 田中さんが教えられること | Codexの知識は不要 |
|------------------------|-----------------|
| コードの読み方、設計の考え方 | エンジニア3-5年の実力 |
| テストの重要性、CIの考え方 | 業務経験 |
| 問題の切り分け方 | 実務スキル |

| 田中さんも後輩と一緒に学ぶこと | |
|-------------------------------|---|
| Codex CLIの操作 | 読者と同じ目線で発見 |
| AGENTS.md、sandbox、exec | 一緒に試行錯誤 |

→ 「AIツールに詳しいから教える」ではなく「エンジニアとして先輩だから導く」
→ Codexについては読者と完全に同じ目線

### Claude Codeの扱い方（最終方針）
- 本文でClaude Codeに言及しない（田中さんに経験がないため）
- 「おわりに」や著者紹介でシリーズとして触れる程度
- 完全に独立した書籍として成立させる

## 5. プロット設計（確定）

### 「なぜCodexか」の動機
高橋部長の号令（「AI活用で開発効率を上げろ」）+ 後輩の推薦のハイブリッド。
- 会社はOpenAI（ChatGPT）の法人契約あり
- 田中さんは「コードを書くAI？」と半信半疑
- 後輩が「Codex CLI、いいですよ」と背中を押す
- 炎上案件を抱えている田中さんが、必要に迫られて試す

### 炎上プロジェクトの概要
```
顧客向けWebサービス（TypeScript / Next.js + API）
- フロントエンド + バックエンドAPI + DB がある程度の規模
- 前任者が退職済み（ドキュメントなし、テストなし、CI放置）
- 納期3週間で機能追加 + バグ修正が必要
- チームは田中さん + 後輩 + あと1-2名（少人数で回すしかない）
```

### 章構成 × ドラマ × Codex差分の対応

**コンセプト**: 「炎上の問題が機能を呼び出す」
CC本は「メンターが機能を段階的に紹介する教科書型」。
Codex本は「問題を解決するために機能を発見するサバイバル型」。

| 章 | 炎上の問題（ドラマ） | 解決に使うCodex機能（差別化） | 感情の動き |
|---|---------------------|--------------------------|-----------|
| 1 | プロジェクトに放り込まれる。コードが読めない、ドキュメントがない | Codex CLIの基本対話（コードを読ませる・質問する） | 「何だこのコード…」→「AIに聞けばいいのか」 |
| 2 | 急いで直そうとして本番相当の環境を壊しかける | **sandbox + 承認モード**（Read-only/Auto/Full Access） | 「やばい…」→「隔離環境で試せるのか」 |
| 3 | 人によってやり方がバラバラ、同じミスが繰り返される | **AGENTS.md** でプロジェクトルールを標準化 | 「また同じバグ…」→「ルールを書けば防げる」 |
| 4 | テストがない。修正のたびに別の箇所が壊れる | テスト生成 + **Plan mode** で設計してから実装 | 「直すと壊れる地獄」→「テストという安全網」 |
| 5 | 手動デプロイで事故。CIが壊れたまま放置されている | **codex exec** で非対話CI/CD自動化 | 「また手動でやるの…」→「自動化できた」 |
| 6 | 納期が迫る。タスクが多すぎて1人では間に合わない | **Codex Cloud** で並列委任 | 「終わらない…」→「並列で回せるのか」 |
| 7 | プロジェクトが安定。この仕組みをチームに定着させたい | **Skills** 作成・共有 + **profiles** で環境切替 | 「自分だけのノウハウ」→「チームの仕組みに」 |
| 8 | プロジェクト完了。振り返りと田中さん自身の変化 | 全体振り返り。AIとの協働の考え方 | 「あの頃の混乱が嘘みたい」 |

### CC本とのドラマ構造の違い

| 観点 | CC本 | Codex本 |
|------|------|---------|
| 学びの動機 | 「もっとうまくなりたい」（成長欲求） | 「今これを消さないとまずい」（生存本能） |
| 機能の導入 | メンターが段階的に紹介 | 問題が機能を呼び出す |
| 読者の感情 | 「自分も佐藤さんみたいに教わりたい」 | 「この状況わかる。で、どう解決するの？」 |
| 章の独立性 | 前章を読んでいないと理解しにくい | 各章の問題が独立 |
