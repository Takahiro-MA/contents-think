## 1. Core Thesis（核となる主張）

**「AIコーディングエージェントは、炎上プロジェクトの"消火器"ではない。問題を1つずつ分解し、安全に解決していく"協働パートナー"だ。Codex CLIは、その協働を最もシンプルに始められる入り口である。」**

補足: 本書の主張は「Codex CLIの操作マニュアル」ではありません。炎上プロジェクト——ドキュメントなし、テストなし、前任者退職済み、納期3週間——という「よくある修羅場」に放り込まれたエンジニアが、後輩と一緒にCodex CLIを使い始め、問題を1つずつ解決していく物語を通じて、「AIと一緒にコードを書く」とはどういうことかを読者に追体験させることが目的です。

大切なのは「AIに丸投げする」ことではなく「AIと協働する」こと。自分の頭で問題を切り分け、AIに実装を手伝ってもらい、AIの出力を自分の目でレビューする。この「人間×AI」の協働ループを回せるエンジニアこそが、AI駆動開発時代に最も価値を発揮する——それが本書の核心メッセージです。

本書はClaude Code本とは完全に独立した書籍として成立します。田中さんにとってCodex CLIが「初めてのAIコーディングツール体験」であり、読者と田中さんが同じ目線でCodexを発見していく構成です。

## 3. 読者の「具体的な痛み」トップ5

### 痛み1: 「前任者が退職して、ドキュメントのないコードベースを引き継いだ」絶望
> コードは動いている。でも「なぜこう書かれているか」が分からない。READMEはほぼ空で、Wikiは更新が止まって半年。IDE上でクラスをたどっても依存関係が複雑すぎて全体像が見えない。誰かに聞きたいけど、前任者はもういない。コードベースを「読める相手」がいれば——。

### 痛み2: 「急いで直そうとして、本番環境を壊しかけた」恐怖
> 納期に追われてコードを直したら、ステージング環境でデータを壊してしまった。本番じゃなくてよかったけど、次は本番かもしれない。「安全に試せる場所」がないまま修正を重ねるのは、綱渡りをしている気分。怖くて手が動かない。

### 痛み3: 「人によってやり方がバラバラで、同じミスが繰り返される」苛立ち
> コーディング規約はあるけど誰も守っていない。命名規則もエラーハンドリングも人によって違う。PRレビューのたびに同じ指摘を繰り返す。「ルールを覚えてくれるAI」がいれば、この無駄な繰り返しから解放されるのに。

### 痛み4: 「テストがない。修正するたびに別の箇所が壊れる」無限ループ
> テストカバレッジはほぼゼロ。バグを1つ直すと別のバグが2つ出てくる。修正のたびにデグレが発生し、「触らなければよかった」と後悔する。テストを書く時間もないし、既存コードのテストをゼロから書く気力もない。

### 痛み5: 「納期が迫っているのに、タスクが多すぎて1人では間に合わない」焦燥
> やるべきことは見えている。でも物理的に時間が足りない。手動デプロイは毎回ヒヤヒヤするし、CIは壊れたまま放置されている。「自分が3人いれば」と何度思ったか。タスクを並列に処理できる方法があれば——。

## 4. タイトル・サブタイトル候補（5案）

### 案1（第2候補）
- **タイトル:** 炎上プロジェクトに「助っ人」が来た
- **サブタイトル:** Codex CLIで始めるAI駆動開発サバイバル物語
- **選定理由:** 「炎上プロジェクト」で現場感を演出し、「助っ人」でAIの役割を直感的に表現します。「サバイバル」で本書の連作短編型の構造を示唆します

### 案2
- **タイトル:** コードの海で溺れたら、AIに手を伸ばせ
- **サブタイトル:** Codex CLIと後輩と駆け抜けた炎上案件の21日間
- **選定理由:** 「溺れる」で読者の痛みに共感し、「手を伸ばせ」で行動を促します。「21日間」で物語のスケール感を伝えます

### 案3（推奨 — 読者レビューで最も共感を得た案）
- **タイトル:** ドキュメントなし、テストなし、前任者なし
- **サブタイトル:** 絶望のプロジェクトをCodex CLIで救った物語
- **選定理由:** 「なし」の三連でリズムを作り、炎上プロジェクトの典型パターンを一言で伝えます。共感フックが強い構成です。読者レビューで最も響いたタイトル案

### 案4
- **タイトル:** 「このコード、誰が書いたんですか？」
- **サブタイトル:** Codex CLIで読み解く炎上プロジェクトの物語
- **選定理由:** 多くのエンジニアが心当たりのある台詞をタイトルに。「読み解く」でAIによるコードベース理解という本書のキーテーマを暗示します

### 案5
- **タイトル:** 納期3週間、戦力はAIと後輩
- **サブタイトル:** Codex CLIで炎上案件を立て直すエンジニアの記録
- **選定理由:** 制約条件を並べることで「この状況どうする？」と読者の好奇心を引きます。「エンジニアの記録」でリアリティを演出します

## 6. 章構成（全8章）

### 各章共通のフォーマット

```
1. 章タイトルページ（田中さんの状況を一言で表す引用文）
2. 問題発生パート: 炎上の問題に直面する（1,500-2,000字）
3. 試行錯誤パート: 田中さんと宮本がCodexで解決を試みる（2,000-2,500字）
4. 解説パート: 学んだ内容の整理（Codex固有の機能解説・コマンド例付き）（2,500-3,000字）
5. 解決パート: 問題が解決される（1,500-2,000字）
6. 振り返りパート: 田中さんの気づき（500-800字）
7. 「やってみよう」コーナー: 読者向け実践ワーク（500-800字）
8. 次回予告（200-300字）
```

> **全体の物語アーク:** 炎上に放り込まれる（第1章）→ 安全に試せる仕組みを知る（第2章）→ チームのルールを標準化する（第3章）→ テストで安全網を張る（第4章）→ CI/CDを自動化する（第5章）→ 並列委任で時間を稼ぐ（第6章）→ チームの仕組みとして定着させる（第7章）→ 振り返りと田中さん自身の変化（第8章）

> **CC本とのドラマ構造の違い:** CC本は「メンターが機能を段階的に紹介する教科書型」。Codex本は「問題を解決するために機能を発見するサバイバル型」。問題が機能を呼び出します。

### 第1章: 「このコード、誰が書いたんですか？」 —— 炎上プロジェクトに放り込まれる

**引用文（冒頭）:**
> 「800ファイル、テストなし、ドキュメントなし、前任者なし。これが"プロジェクト"と呼べるのか——」

**田中さんの問題:**
高橋部長から「顧客向けWebサービスの保守開発プロジェクトに入ってくれ」と言われた田中さん。前任者は3ヶ月前に退職済み。引き継ぎは「READMEに少し書いてあるはず」の一言だけ。リポジトリをクローンすると、TypeScript/Next.js + APIのコードベースで、ファイル数は800以上。READMEはほぼ空。テストはゼロ。CIは半年前に壊れたまま放置。納期は3週間で機能追加＋バグ修正が必要。チームは田中さん、後輩の宮本、インフラ担当の永井の3人。

**学ぶ内容:**
1. Codex CLIとは何か——ChatGPTとの違い、CLIベースのAIコーディングエージェントの基本概念
2. インストールと初期セットアップ——`npm install -g @openai/codex`、ChatGPTアカウントでのログイン
3. コードベース全体をAIに「読ませる」——「このリポジトリの全体構造を説明して」から始まる理解
4. AIとの対話でコードを探索する——依存関係、エントリーポイント、データフローの把握

**ストーリーライン:**
高橋部長から炎上プロジェクトへのアサインを告げられた田中さん。リポジトリをクローンしてIDEで開くが、ファイル数の多さと構造の複雑さに圧倒されます。grepで検索しても同じ関数名が何十箇所もヒットして絞り込めません。そこへ後輩の宮本が「田中さん、Codex CLIって知ってます？ ChatGPTの契約そのままで使えるみたいですよ」と声をかけてきます。半信半疑でインストールし、「このリポジトリの全体構造を説明して」と入力すると、パッケージ構造、主要なAPIエンドポイント、データベーステーブルの関係が整理されて返ってきます。「3日はかかると思った全体把握が...」と田中さんは目を見張ります。

**実践ワーク:**
- [ ] Codex CLIをインストールし、`codex`と打って起動してみる
- [ ] 自分の担当プロジェクトで「このリポジトリの全体構造を説明して」と聞いてみる
- [ ] AIの回答と自分の理解を照らし合わせ、「知らなかったこと」を1つ見つける

### 第2章: 「やばい、ステージング壊した...」 —— sandboxと承認モードで安全に試す

**引用文（冒頭）:**
> 「急いで直そうとした。そしたら余計に壊した。——慎重にやりたいのに、時間がない」

**田中さんの問題:**
コードベースの全体像は掴めてきましたが、納期のプレッシャーで急いでバグ修正に取りかかった田中さん。ネットで見かけた`--dangerously-bypass-approvals-and-sandbox`フラグ（通称 --yolo）を安易に使い、sandboxも承認確認も無効化した状態でCodexに修正を依頼したところ、ローカル環境のデータベースを意図せず書き換えてしまいます。「安全装置を外してはいけなかった」——安全に試行錯誤できる仕組みの重要性を痛感します。

**学ぶ内容:**
1. sandbox（サンドボックス）の仕組み——カーネル層でファイルシステムとネットワークを隔離する安全設計
2. 承認モードの2軸設計——sandbox_mode（`read-only` / `workspace-write` / `danger-full-access`）とapproval_policy（`untrusted` / `on-request` / `never`）の組み合わせ。UIラベルとしては「Read-only / Auto / Full Access」が表示されます
3. `--full-auto`フラグの正体——`workspace-write`（ワークスペース内のみ書き込み可）+ `on-request`（必要時に承認を求める）のconvenience alias
4. 「まずRead-onlyで試す→安全を確認してからAutoに切り替える」段階的アプローチ。`--dangerously-bypass-approvals-and-sandbox`（通称 --yolo）の存在と危険性

📘 技術解説ボックス: Codex CLIの安全設計は「2つの軸」で考える

| | approval: untrusted | approval: on-request | approval: never |
|---|---|---|---|
| sandbox: read-only | 最も安全。すべて承認必須 | 読み取りのみ自動 | 読み取りのみ（変更不可） |
| sandbox: workspace-write | 作業Dir内は自動、外部は承認 | **Auto（デフォルト）** | 作業Dir内で自由に変更 |
| sandbox: danger-full-access | 全アクセス可、承認必須 | 全アクセス可、要求時承認 | **--yolo（非推奨）** |

便利なエイリアス:
- `--full-auto` = workspace-write + on-request（低リスクな自動化プリセット）
- `--yolo` = danger-full-access + never（非推奨。本書では使わないことを推奨）

**ストーリーライン:**
焦った田中さんは、ネットで見かけた`--dangerously-bypass-approvals-and-sandbox`フラグ（通称 --yolo）を安易に付けてCodexを実行してしまいます。sandbox（隔離環境）も承認確認もすべてバイパスされた状態でマイグレーションスクリプトが走り、ローカルのデータベースが書き換わってしまいます。「やばい...」と青ざめる田中さんに、宮本が「田中さん、sandboxっていう機能があるみたいですよ」と声をかけます。Codexのsandbox機能——ファイルシステムとネットワークをOS層で隔離する仕組み——を知った田中さんは、「まずRead-onlyモードでAIの提案だけ見る→内容を確認してからAutoに切り替える」という段階的なワークフローを確立します。宮本は「隔離された環境で試せるって、砂場で安心して実験するみたいですね」と笑います。

**実践ワーク:**

### 反論1: 「Claude Codeとの違いは何？ Claude Codeの本もあるんでしょ？」

本書はCodex CLIの独立した入門書であり、Claude Codeとの比較を前提としていません。読者がClaude Codeを知らなくても、Codex CLIの世界観の中で完結する内容です。もし両方を知っている読者がいた場合のために補足すると、Codex CLIはOpenAIエコシステム上で動作し、sandbox＋承認モード（カーネル層の隔離）による安全設計、AGENTS.md（オープン標準）によるルール標準化、`codex exec`（非対話モード）によるCI/CD統合、Codex Cloudによるクラウド並列委任といったCodex固有の機能群を持っています。本書はこれらの機能を炎上プロジェクトの文脈で実践的に学ぶ構成であり、「どちらが優れているか」の比較ではなく「Codexで何ができるか」にフォーカスしています。

### 反論2: 「AIに任せて大丈夫？ コードの品質が心配」

**回答:**
本書はまさにこの懸念に正面から向き合います。第2章で「AIが意図せずデータベースを書き換えた」失敗を描き、sandbox＋承認モードで安全に制御する方法を示します。第4章ではAI生成テストの2割が修正必要だったエピソードを通じ、「AIの出力は常にレビューする」原則を強調します。本書のメッセージは「AIに丸投げすれば安全」ではなく「人間がレビューする前提で、AIに任せられる部分を最大化する」です。

### 反論3: 「物語形式は回りくどい。コマンドリファレンスだけ教えて」

**回答:**
コマンドリファレンスはCodex CLIの公式ドキュメント（codex.openai.com/docs）に充実しています。しかし多くのエンジニアは「コマンドは知っているが、どの場面で使えばいいか分からない」状態にあります。物語形式は、読者の「感情」——炎上プロジェクトの不安、AIへの不信、チーム展開の壁——に寄り添い、「自分の現場でもこうすればいいのか」という具体的なイメージを与えます。田中さんシリーズの既刊が証明しているように、物語形式には技術書にない「読了率の高さ」と「行動変容力」があります。

### 反論4: 「ChatGPT Plusの$20で使えるっていうけど、制限があるんじゃ？」

**回答:**
第1章のセットアップパートで、ChatGPT Plus（$20/月）の範囲で使えること、API利用時の課金体系との違い、使用量上限の目安を誠実に説明します。「今の契約のまま始められる」ことは事実ですが、ヘビーユースでは追加課金が発生しうることも隠しません。具体的な目安として、日常的なコード理解・テスト生成・CI自動化であればPlus $20/月の範囲内で十分に活用できます。大量のCloud並列委任やモデルの高頻度利用が必要な場合はPro（$200/月）の検討が必要です。読者が「試すハードル」を感じないよう配慮しつつ、過度な期待を煽らない誠実な記述を心がけます。

### 反論5: 「OSSなのはいいけど、エンタープライズで使えるの？」

**回答:**
第7章のチーム展開パートで、AGENTS.mdの標準化・profilesによる環境制御・codex execによるCI/CD統合がエンタープライズ運用の基盤になることを示します。Apache-2.0ライセンスによる商用利用・改変・再配布の自由度も、企業内ツールとしての安心感を与えます。ただし本書はエンタープライズガバナンスの教科書ではないため、高度な承認フロー設計や大規模組織への展開は「発展的な課題」として位置づけ、深入りはしません。
