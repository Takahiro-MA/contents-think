**E5 評価メモ（2026-07-01、格上げ再構築）:** Authority/Passion/Feasibility は H（AIエージェント3部作でCI/CDに地続き＋著者がself-hosted runner構築の当事者＋田中さんシリーズの型確立）。Audience も H（CI/CDは全エンジニア必須＋既刊書籍評価に「CI/CD知りたかった」の実需が顕在化＝実証済み）。トップ層(15)と分けるのは Differentiation(M) のみ——強い競合『GitHub CI/CD実践ガイド』（技評2024、設計・運用・self-hosted網羅）が存在。ただし競合は中級者向けハンズオン/リファレンス型で、本企画は①物語形式で初学者に橋渡し②AI時代の"設計判断"という時代性③実行環境の"地図"（GitHub-hosted/self-hosted/閉域を判断軸で語る）④基礎→応用の学習設計、で明確に棲み分け可能。この4点を旗に立てれば Differentiation は H（合計15・トップ層）に届く。逆に「GitHub Actionsの使い方本」に寄せると競合に埋もれ M 止まり。

**E10 評価メモ（2026-06-23、主題確定後に更新）:** 著者がアプリ開発（モバイル含む）の実務者であるため Authority/Passion/Feasibility は H。**Differentiation も主題確定により M→H**。核は"ラストワンマイル"——「Codexでアプリ作ったら簡単だった」と言う人は増えたが、**ローカル/Webで動くものを App Store に公開するところまで辿り着く人は少ない**。その谷（Apple Developer登録・署名/プロビジョニング・App Store Connect・審査対応・スクショ/プライバシー表示）はAIコーディング系コンテンツがほぼ素通りする領域で、ここを「簡単なアプリ作成→ストア公開」まで一本のロードマップで伴走するのが他にない価値。市場確認の既刊（Dify／つくりながら学ぶ生成AIアプリ＆エージェント／Replit入門 等）は"LLM/AIエージェントを組み込んだアプリ"を作る本で、本企画とはベクトルが別。**残る注意は2点だけ:** (1)タイトルが「生成AIアプリ(LLM)開発」と混同されないよう、サブタイトル等で「App Storeまで」を前面に出す、(2)自社AI駆動開発3部作＋E1との食い合いは「モバイル＋ストア公開」を明確な軸にすれば回避可能。**合計15・トップ層（A1/B1/E1/E2と同格）。**

**E10 企画メモ（深掘り種・2026-06-23）:**
- **ターゲット:** 完全初心者層（プログラミング未経験〜浅い、非エンジニア含む）。「AIに任せれば自分でもアプリが作れるのでは」と思っている層。
- **ゴール:** ゼロ → App Store 公開まで、一本のロードマップで伴走。
- **スコープ:** **iOS / App Store 主体**。Android も扱う（完全には閉じない）が従。とくに **Android は個人アカウントだと本番公開前にクローズドテスト要件（テスター人数×期間）があり、法人は緩い** という"つまずき"を差として取り上げる ※具体要件は時期で変わるため執筆時に公式で再確認。
- **カバー範囲（章の種）:**
  1. そもそも論の言語化 —— アプリ開発とは／モバイルアプリとは／プログラミング言語とは（初心者の最初の霧を晴らす）
  2. AIに任せるにしても「中身は何の言語/スタックで組むのか・なぜか」 —— 完全ブラックボックスにしない最低限の理解（"動くけど説明できない"不安への対処。田中さんシリーズの縦串とも接続）
  3. AIで実際に作る —— 簡単なアプリを1本（物語の背骨になる題材）
  4. **ラストワンマイル(iOS・本書の肝):** Apple Developer登録 → 署名/プロビジョニング → App Store Connect → TestFlight → 審査対応 → スクショ/プライバシー表示 → 公開
  5. Android(Google Play)の違い（従）—— 個人のクローズドテスト要件など、iOSとの差分を簡潔に
- **編集注記:** タイトル/サブタイトルは「**App Storeまで**」を前面に出し、「生成AIアプリ(LLM)開発」ジャンルとの混同を避ける。

**E10 シリーズ位置づけ・構成方針（2026-06-23 確定）:**
- **形式: 田中さんシリーズのスピンオフ（番外編）。** 主人公＝完全初心者の新キャラ（読者の分身・非エンジニア）、**田中さんは初の"教える側"＝メンター**として登場。田中さん自身は経験者なので「学ぶ側」にはできない（＝主人公にはできない）のが唯一にして最大の制約。田中さんの成長アーク「教わる→教える」としても収まりが良い。アプリ開発は田中さんの本業ど真ん中なのでメンター必然性が高い（キャリアピボットより取り込みやすい）。
- **ブランド注記:** 既刊読者はエンジニア層。完全初心者本を「田中さんシリーズ」名で出すと既刊読者には刺さりにくいので、「**番外編／スピンオフ**」表記で橋渡しし、本体は初心者ファネルの新規開拓と割り切る。文体ルール（ですます調・さん付け等）はそのまま継承。
- **構成: 既存テンプレ（冒頭独白→シーン→📘技術解説→☕コラム→振り返り→やってみよう→次回予告）を踏襲。ただし適応3点:**

**E10 2冊構想・スコープ確定（2026-06-23）:**
- **2冊に分冊（入門→初級のラダー）。C＝1冊目（入門）先行、B＝2冊目（初級）は続編候補。**
  - **C（入門・1冊目）**: 主人公＝生活者/育児系の非エンジニア。題材＝純ローカルの最小アプリ（例：子どものお手伝いスタンプ）。技術＝UI＋ローカル保存＋通知、バックエンドなし。**本体＝公開のラストワンマイル（ゼロ→App Store公開）をフル解説**。"こんな低いハードルでもアプリ公開まで"が最広フック。
  - **B（初級・2冊目）**: 主人公＝趣味/個人事業（トレーナー/作家等）。題材＝もう少し本格的なアプリ。技術＝＋外部API/クラウド保存・同期。**公開手順は復習のみ**（Cで習得済み前提）。
- **差別化軸の鉄則**: 公開パイプラインはCの本体、Bでは復習だけ（2冊目が焼き直しに見えるのを防ぐ）。Bの主役は"アプリの中身を深める技術"。
- **執筆順の規律**: **Cを単独で完成・出版→反応を見てB**。両にらみの並行執筆はしない（シリーズもののテンプレ使い回し共倒れを回避。1冊集中の方が成功確率高い）。CにB予告（次回予告）を仕込んで橋渡し。
- **ボリューム懸念への結論**: Cは薄くならない。むしろ公開のラストワンマイル（Apple Developer登録・**署名/プロビジョニング**・App Store Connect・スクショ/プライバシー・TestFlight・審査/リジェクト対応）が分量豊富かつ差別化の本体で、"過密"の方がリスク。**満足感の設計＝達成感を「自分のアプリがApp Storeに並んだ」という公開体験に置く（アプリの高度さで報いない）＋ Cを"単純アプリなら一人で作って公開できる"完結スキルにする（Bの予告編＝未完成スキルにしない）。**
- **C ドラフト目次（9章案）**: ①アプリはどう世に出るか（全体像＋そもそも論）②AIに頼む前に（スタック選択・環境・AIとの付き合い方）③画面を作る（UI）④データを覚えさせる（ローカル保存）⑤通知でアプリらしく ⑥公開準備①Apple Developer登録・署名/プロビジョニング ⑦公開準備②App Store Connect・スクショ・プライバシー ⑧TestFlightと審査（提出・リジェクト対応）⑨公開！とその後（更新の回し方／B予告）。公開関連6〜9で4章＝十分な一冊。
- **任意の安全弁**: Cにストレッチ1個（軽い外部API or 共有）をボーナス章で入れる手はあるが、Bの主題を食うので基本は「やってみよう応用編」で次に送る。
- **未確定**: C主人公の人物像、主人公の張り方（案ア＝別人物＋田中さん軸 ／ 案イ＝同一人物レベルアップ。案ア推奨）。

**E10 B（2冊目・初級）内容スコープ（2026-06-23）:**
- **「コードは全部AIに任せる」前提だと、Bの中身はむしろ増える。** 本の中身が「言語の書き方」→「判断・統合・運用」に移り、アプリが複雑になるほど面積が増えるため。Bの心配は"薄さ"でなく"散らかり"。
- **AIが代行しない＝Bの中身:** クラウド/バックエンド選定・データ設計・権限（Firebase/Supabase等）、外部API（**キー取得と安全な保管**・docの読み方・**失敗処理**）、認証（Sign in with Apple・**アプリ内アカウント削除のApp Store要件**）、AI生成コードのデバッグ、セキュリティ/プライバシー表示の深化、**クラウドの料金感覚**、richアプリが招く審査の変化、大きめアプリのAIへの渡し方（要件分解・コンテキスト管理＝シリーズの縦串）、公開後の運用（更新・クラッシュ監視・レビュー対応・改善ループ）。
- **背骨: 「クラウドデータ＋外部API 1つ」を持つアプリ1本に固定。** この一歩を入れるだけで上記が芋づるで"必然"登場し、寄せ集めにならない。
- **高度:** 「読めて・指示できて・検証できる」レベル（手で書ける、ではない）。シリーズの「動くけど説明できる」の一段上版。
- **B ドラフト目次（8章案）:** ①「動く」→「使える」へ ②何を作るかAIにどう伝えるか（spec的思考）③データをクラウドに置く ④外部サービスと繋ぐ（API）⑤ログインを入れる（任意）⑥壊れたときに直す（デバッグ）⑦安全とお金 ⑧公開（復習）と運用。
- **Cを書く意義:** Bの範囲を押さえた上でCを書くと、CとBの境界（Cは公開パイプライン＋ローカル最小、Bは中身の技術深掘り）が明確になり、Cが"完結スキル"として綺麗にまとまる。

**E5 企画メモ（深掘り種・2026-07-01）:**
- **主軸:** AIがYAMLを書ける時代の、CI/CDの"環境選定と設計判断"を学ぶ。田中さん主人公・1冊・既刊程度のボリューム（8章想定）。
- **物語構造＝異動2部構成（1人が環境の違う2現場を経験＝"時間の広がり"で複数環境を1物語に両立）:**
  - **第1部（基礎・5章）:** GitHub Actions × クラウド。CI/CDの概念そのもの（テスト自動化・パイプライン設計・デプロイ戦略）を、インフラの雑音なしに厚く学ぶ。runner/marketplace/Secretsが"用意されている"世界。
  - **第2部（応用・3章）:** 異動で閉域現場へ（GitLab × self-hosted runner）。概念は継承、実装だけ変わる（Kiro本のReact→Expo移植と同じ「1つの頭・2つの体」構造）。
- **配分の根拠（著者の主観でなく客観の学習順序で決定）:** モダン側＝基礎（CI/CDの本質に集中できる）、閉域側＝応用（基礎の再適用＋インフラ固有対処）。ゆえに基礎を厚く（5:3）。著者のself-hosted実体験は"分量を増やす"のでなく"第2部のリアリティ担保＋第1部でどこを丁寧に書くか"に反映。
- **学びのクライマックス:** 第1部で"当たり前"だと思ったもの（runnerが湧く/marketplace/Secrets/クラウドdeploy）が、第2部の閉域で全部"自前"になると気づく対比。「便利さの正体を、それが無い環境で初めて理解する」＝既刊のどれもやっていない構造。
- **差別化の旗（Differentiation M→H の鍵）:** ①物語形式で初学者に橋渡し ②AI時代の設計判断という時代性 ③実行環境の"地図"（GitHub-hosted/self-hosted/閉域を判断軸で語る）④基礎→応用の学習設計。「GitHub Actionsの使い方本」に寄せない（競合『GitHub CI/CD実践ガイド』に埋もれる）。
- **現場設定:** フレキシブル（thinking-hub作成時に確定）。後半の閉域現場は自治体/製造など"閉域が必須な理由が自明"な業種を仮置き（Kiro本の自治体プロダクトと地続きにできる）。
