# レビュー2: 技術専門家視点（SQL正確性）

## A（必須修正）

### A-1: NULL解説の精度向上
「NULLの扱い」という表現を「NULLと三値論理」に変更する。NULLを含む比較がTRUE/FALSEではなくUNKNOWNになる三値論理の概念を追記し、IS NULL / IS NOT NULLを使うべき理由を正確に説明する。`WHERE column = NULL` が機能しない理由を具体例で示す。

### A-2: 第2正規形・第3正規形の定義精度向上
正規形の定義説明を正確にする。第2正規形は「部分関数従属の排除」、第3正規形は「推移的関数従属の排除」であることを明示し、それぞれの定義を誤りのない形で記述する。実務でよく見る違反パターンを具体例に使うと読者の理解を助ける。

### A-3: ウィンドウ関数のWHERE句制約を明記
ROW_NUMBER()等のウィンドウ関数の結果はWHERE句で直接使用できないという制約を第6章（またはウィンドウ関数解説箇所）に明記する。CTEまたはサブクエリで包む必要があることを示し、第8章のCTE解説への伏線として機能させる。具体的なエラーパターンと正しい書き方をセットで示す。

### A-4: BETWEEN句のTIMESTAMP型の落とし穴を追記
BETWEEN句が両端の値を含む（閉区間）動作であること、およびTIMESTAMP型に対してBETWEENを使う際の境界値問題（日付の23:59:59.999...問題）を具体例で追記する。`>= '2024-01-01' AND < '2024-02-01'` のように明示的な範囲指定を推奨する表現を追加する。

### A-5: DATE_TRUNCのPostgreSQL固有性を注記
DATE_TRUNC関数はPostgreSQL固有の関数であることを明記し、SQL標準のEXTRACT関数との違いを補足する。MySQL/Oracle/SQL Server等の対応する関数（DATE_FORMAT, TRUNC等）への言及も添えることで、他DBMSへの移植時の注意喚起とする。

## B（推奨修正）

### B-1: INDEX効果の数値修正
ストーリー中に登場するINDEX効果の数値を現実的な値に修正する。「30秒→0.1秒」という改善例は理論上は起こり得るが、一般的なユースケースでは誇張と受け取られる可能性がある。「30秒→0.5秒」程度の現実的な数値に変更する。

### B-2: SQL標準と方言の具体化（技術面）
SQL標準（ISO/IEC 9075）として規定されている構文と、各DBMSの方言を具体的に列挙する。特に本書がPostgreSQLを主DBMSとして採用している場合、MySQL/Oracle/SQL Serverとの主要な差異（LIMIT vs TOP vs ROWNUM、文字列連結演算子 || vs +、日付関数等）を付録または注記として整理する。

### B-3: 正規化の実務的なトレードオフを追記
正規化の解説において、正規化によってクエリが複雑になる（JOIN数が増える）トレードオフを明記する。実務では意図的に非正規化するケースがあること、その判断基準（読み取り性能が書き込み整合性より重要な場合等）を補足することで、ペルソナCに「設計判断の軸」を提供する。

### B-4: EXPLAIN ANALYZEの読み方を章立てに含める
ペルソナCの悩みとして「EXPLAIN ANALYZEの読み方が分からない」が挙げられているが、仕様書の章構成にEXPLAINの解説が明示されているか確認する。第7章または第9章で、Seq Scan / Index Scan / Nested Loop等の基本的な実行計画の読み方を1シーン分追加する。

### B-5: サブクエリとCTEのパフォーマンス特性を明記
サブクエリとCTE（WITH句）は書き方が異なるだけでなく、DBMSによって最適化の挙動が異なる点を注記として追加する。PostgreSQLではCTEが最適化フェンスとして機能する（v12以前）ことへの言及など、中級者（ペルソナC）の知識欲を満たす情報を盛り込む。

## C（改善提案）

### C-1: INDEX効果の数値修正（ストーリーライン整合性）
