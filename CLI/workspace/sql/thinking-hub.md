## 1. Core Thesis（核となる主張）

**「SQLは"データベースを操作するコマンド"ではない。"集合で世界を捉える思考法"である。Excelの行を1行ずつ見る思考から、テーブル全体を集合として扱うリレーショナル思考へ——このパラダイムシフトを経験したエンジニアは、データの見え方が根本的に変わる。」**

補足: 本書の主張は「SQLの文法リファレンス」ではない。「なぜSELECT *しか書けないのか」「なぜJOINが怖いのか」「なぜサブクエリで頭が混乱するのか」——その原因はSQL構文の難しさではなく、「1行ずつ処理する手続き型思考」と「集合で考える宣言型思考」のギャップにある。田中さんが日常業務でぶつかるデータの課題を通じて、このパラダイムシフトを体験する物語である。

大切なのは「SQLを暗記する」ことではなく「データをどう捉えるかの思考法を身につける」こと。テーブル設計の意図を読み解き、JOINで関係性をたどり、集約関数で全体像を掴み、ウィンドウ関数で文脈の中のデータを見る。この「リレーショナル思考」を身につけたエンジニアは、どのデータベース製品を使っても、どんなBI・分析ツールに触れても、データと対話できる——それが本書の核心メッセージである。

## 3. 読者の「具体的な痛み」トップ5

### 痛み1: 「SELECT * しか書けない。JOINが出てくると手が止まる」問題
> テーブル1つからデータを取るのはできる。だが2つ以上のテーブルを結合するJOINになると、INNER JOIN、LEFT JOIN、RIGHT JOINの違いが曖昧で、書くたびにググっている。ONの後の条件も「どのカラムとどのカラムを繋げばいいのか」が直感的に分からない。結果、JOINを避けてアプリケーション側でデータを結合する非効率な実装をしてしまう。

### 痛み2: 「Excelの限界を感じているが、SQLへの移行方法が分からない」壁
> Excelで10万行のCSVを開くとフリーズする。VLOOKUPの計算に数分かかる。ピボットテーブルの集計軸を変えるたびに作り直し。「SQLなら一瞬で終わる」と聞くが、「そもそもどうやってDBにデータを入れるのか」「SQLとExcelの操作はどう対応するのか」が分からない。SQLの入門書はCREATE TABLEから始まるが、「自分はテーブルを作りたいのではなく、データを見たいだけ」という温度差を感じる。

### 痛み3: 「ORMが生成するSQLが遅いと言われても、何が問題か分からない」苛立ち
> ORMでfindAllやfindByIdを呼ぶだけで動くから、裏で何が起きているか考えたことがない。ある日「N+1問題が発生している」と指摘され、ORMが裏で100回のSELECTを発行していることに気づく。だがJOIN FETCHやEager Loadingの設定を変えると別の問題が起き、「結局生SQLを書いた方が早い」場面が増える。ORMの裏側で何が起きているかを理解するためにも、SQLの基礎力が必要だと痛感する。

### 痛み4: 「サブクエリやウィンドウ関数が出てくると読めない」恐怖
> 先輩やシニアエンジニアが書いたSQLを読む場面で、サブクエリが3段ネストしていたり、PARTITION BY付きのウィンドウ関数が使われていると、完全にお手上げ。何をやっているのか追えないので、修正も怖くてできない。「読めないSQLは触れない」というのが自分のボトルネックだと気づいているが、どう克服すればいいか分からない。

### 痛み5: 「テーブル設計のレビューができない。正規化が分かったようで分からない」不安
> 「第3正規形まで正規化する」と教科書には書いてあるが、実務ではパフォーマンスのために非正規化することもある。その判断基準が分からない。後輩に「このテーブル設計、大丈夫ですか？」と聞かれても、「たぶん大丈夫」としか言えない。正規化の理論と実務の折り合いを自信を持って説明できるようになりたい。

### 第1章: SELECT * FROM my_career WHERE skill = 'SQL' —— データと向き合う日がやってきた

**三幕構造:**
- **壁:** ORMに頼りきりでSQLが書けない。障害対応でDBを直接見る場面で手が止まる
- **仕組み:** SQLの基本構文（SELECT/FROM/WHERE）と「集合で考える」思考法の入口
- **結果:** 単一テーブルからデータを自在に取得でき、「SQLは行を1行ずつ見るのではなく、条件に合う集合を返す」と理解する

**田中さんの課題:**
高橋部長から「社内のデータ分析基盤を整備したい。まずは既存システムのデータベースから必要なデータを抽出できるようになってくれ」と依頼された田中。ORMでfindAllやfindByIdは使えるが、psqlでDBに直接接続してSQLを書いたことはほとんどない。障害対応で「usersテーブルのステータス別の件数を出して」と頼まれたとき、SELECT * FROM usersで全件取得してExcelに貼り付け、手動でフィルタをかけていた。

**学ぶ内容:**
1. SQLとは何か —— 「手続き型」と「宣言型」の違い。「どうやって取るか」ではなく「何が欲しいか」を書く
2. SELECT/FROM/WHERE の基本 —— 条件に合うデータの集合を取得する
3. ORDER BY / LIMIT —— 並び替えと件数制限
4. 「Excelフィルタ」と「WHERE句」の対応 —— Excel脳からの架け橋
5. NULLの扱い —— 「値がない」は「ゼロ」や「空文字」とは違う

**ストーリーライン:**
高橋部長から「データ分析基盤の整備」を任された田中。「とりあえずユーザー数を月別に出してくれ」と言われ、ORMでUser.findAll()を呼び、結果をExcelに貼り付けて手動集計し始める。数万行のデータにExcelが悲鳴を上げる中、佐藤先輩が通りかかり画面を覗く。「田中くん、それ...SQLで一行書けば終わるよ」。佐藤先輩はpsqlを開き、WHERE句で条件を絞り、ORDER BYで並び替えるクエリを実演する。田中は「Excelでフィルタして並び替えてたのと同じことが、一行で...」と驚く。佐藤先輩は「大事なのはね、SQLは"1行ずつ処理する"のではなく"条件に合う集合をまとめて返す"ということ。Excelは目で1行ずつ確認するでしょ？ SQLは"この条件に合う全部のデータ"を一気に取ってくるの。この違いが分かると、データの見え方が変わるよ」と語る。

**実践ワーク:**
- [ ] psql（またはpgAdmin等のGUIツール）でPostgreSQLに接続し、SELECT * FROM テーブル名 LIMIT 10; を実行してみる
- [ ] WHERE句で条件を指定し、特定のデータだけを取得してみる（例: WHERE status = 'active'）
- [ ] 普段Excelでやっている「フィルタ→並び替え」の操作を、SQLのWHERE + ORDER BYで書き換えてみる

### 第2章: JOINは「ホチキス留め」—— テーブルとテーブルを繋ぐ

**三幕構造:**
- **壁:** 2つのテーブルにまたがるデータが必要だが、JOINが書けずアプリ側でループ結合している
- **仕組み:** INNER JOIN / LEFT JOINの概念と「関係」で考える思考法
- **結果:** JOINでテーブルを結合し、「データは1つのテーブルに全部入れるのではなく、関係で繋がっている」と理解する

**田中さんの課題:**
「ユーザーごとの注文履歴を一覧で出してほしい」と依頼された田中。usersテーブルとordersテーブルがある。ORMなら user.getOrders() で取れるが、生SQLでは？ 田中は2つのSELECTを別々に実行し、JavaのforEachでユーザーIDをキーにデータを突き合わせる——いわゆるN+1問題のアプリ側バージョンをやってしまう。

**学ぶ内容:**
1. INNER JOINの基本 —— 「両方のテーブルに存在するデータ」を結合する
2. LEFT JOINの基本 —— 「左のテーブルは全件、右は一致するものだけ」。NULLで"ない"が分かる
3. ON句の意味 —— 「どのカラムで繋ぐか」を指定する。外部キーの役割
4. JOINの日常比喩 —— 住所録と電話帳をホチキスで留める。名前が一致する行を横に並べる
5. 複数テーブルのJOIN —— 3テーブル以上の結合。恐れる必要はない、1つずつ繋げるだけ

**ストーリーライン:**
「ユーザーごとの注文金額合計を出してほしい」と頼まれた田中。usersテーブルとordersテーブルを別々にSELECTし、Javaで突き合わせるコードを書き始める。佐藤先輩がコードを見て「田中くん、それ、ORMのN+1問題と同じことを手動でやってるよ」と指摘。佐藤先輩はホワイトボードに2つの表を書き、「住所録と電話帳を想像して。名前が同じ行をホチキスで留めて1枚にする——それがJOIN。SQLでは1行で書けるの」と説明。田中はINNER JOINを書いて実行し、2つのテーブルが1つの結果セットになる瞬間に「ああ、そういうことか」と膝を打つ。さらに「注文がないユーザーも含めたい」場面でLEFT JOINの必要性を体感する。NULLが表示される行を見て「"注文がない"という情報も、データなんですね」と気づく。

**実践ワーク:**
- [ ] 自分のプロジェクトで外部キーで繋がっている2つのテーブルを見つけ、INNER JOINで結合してみる
- [ ] 同じテーブルをLEFT JOINで結合し、NULLが出る行の意味を確認する
- [ ] アプリケーションコードの中で「forEachで別テーブルのデータを取得している箇所」を1つ見つけ、JOINで書き換えるSQLを考えてみる

### 第3章: WHERE句の向こう側 —— 絞り込みの技術を磨く

**三幕構造:**
- **壁:** 複雑な条件指定ができず、とりあえず全件取得してアプリ側でフィルタしている
- **仕組み:** AND/OR/IN/BETWEEN/LIKE/EXISTS等の条件指定と、サブクエリの入口
- **結果:** 「必要なデータだけをDBから返す」思考法が身につき、無駄なデータ転送が減る

**田中さんの課題:**
前章でJOINを覚えた田中に、もう少し複雑な抽出依頼が来る。「先月アクティブだったユーザーのうち、累計注文金額が1万円以上で、かつ東京都在住のユーザーの一覧」。条件が3つ重なると途端にWHERE句の組み立てに迷う。ANDとORの優先順位で間違えてしまい、意図しない結果が返ってくる。

**学ぶ内容:**
1. AND / OR の優先順位と括弧の重要性 —— 意図通りの条件を組み立てる
2. IN句 —— 「このリストのどれかに一致する」
3. BETWEEN —— 範囲指定の便利さと落とし穴（境界値の扱い）
4. LIKE —— パターンマッチング。%と_の使い分け
5. サブクエリ入門 —— WHERE句の中にSELECTを書く。「別の問いの答えを条件にする」
6. EXISTS —— 「存在するかどうか」で絞り込む

**ストーリーライン:**
「先月アクティブ + 累計1万円以上 + 東京都在住」の抽出に挑む田中。WHERE active = true AND total >= 10000 OR prefecture = '東京都' と書いてしまい、ORの優先順位でおかしな結果が返る。佐藤先輩は「条件を日本語で書き出してから、SQLに変換するといいよ。括弧を使って意図を明確にする。数学の式と同じ」とアドバイス。さらに「先月注文したユーザー」をサブクエリで絞り込む方法を教える。田中は「WHERE句の中にSELECTが書ける？ 問いの中に問いがある...」と驚く。佐藤先輩は「そう、SQLは"問いを組み合わせる言語"なの。1つの問いの答えを次の問いの条件にできる。これが手続き型言語のif文とは根本的に違うところ」と語る。

**実践ワーク:**
- [ ] AND/ORを含む3つ以上の条件を組み合わせたWHERE句を書いてみる。括弧の有無で結果が変わることを確認する
- [ ] IN句を使って「特定のカテゴリに属するデータ」を取得してみる
- [ ] サブクエリを使って「別のテーブルの条件でフィルタする」クエリを1つ書いてみる

### 第4章: 「全体像」をつかむ力 —— GROUP BYと集約関数

**三幕構造:**
- **壁:** データの件数や合計を出すのにExcelに貼り付けてピボットテーブルを使っている
- **仕組み:** COUNT/SUM/AVG/MAX/MINとGROUP BY、HAVINGの概念
- **結果:** 「個々のデータ」から「全体の傾向」を一発で掴める。Excelのピボットテーブルから卒業する

**田中さんの課題:**
「部署ごとの月別売上推移を出してほしい」と高橋部長から依頼。田中はSELECT * でデータを全件取得し、Excelに貼り付けてピボットテーブルで集計する。10万行のデータをExcelにエクスポートするのに5分、ピボットの設定に10分、グラフ作成に15分。渡辺さん（データアナリスト）が「それ、GROUP BYで30秒だよ」と声をかける。

**学ぶ内容:**
1. 集約関数の基本 —— COUNT / SUM / AVG / MAX / MIN
2. GROUP BY —— 「グループに分けて、グループごとに集計する」
3. HAVING —— 「集計結果に条件をつける」。WHEREとの違い
4. Excelピボットテーブルとの対応 —— 行ラベル = GROUP BY、値 = 集約関数
5. 集約の組み合わせ —— GROUP BYとJOINを組み合わせて多角的に分析する

**ストーリーライン:**
10万行のデータをExcelに貼り付けてピボットテーブルと格闘する田中。渡辺さんが横から覗いて「田中さん、それSQLで一発ですよ」とpsqlを開く。SELECT department, DATE_TRUNC('month', order_date), SUM(amount) FROM orders GROUP BY 1, 2 ORDER BY 1, 2。3秒で結果が返る。田中は「30分かけてたのが3秒...」と絶句。佐藤先輩は後から「GROUP BYの考え方は、テスト用紙の山分けと同じ。クラス全員のテスト用紙を"科目ごとの山"に分けて、各山の平均点を出す——それがGROUP BY + AVGなの。SQLは"集合をグループに分ける"のが得意。これがExcelとの決定的な違い」と解説。HAVINGについては「WHEREは1枚ずつテスト用紙を見て70点以上だけ残す。HAVINGは山を作った後に"平均80点以上の山だけ残す"。フィルタのタイミングが違うの」と日常比喩で教える。

**実践ワーク:**
- [ ] 自分のプロジェクトのテーブルで、GROUP BY + COUNTを使って「カテゴリ別の件数」を出してみる
- [ ] SUM/AVGを使って「グループ別の合計・平均」を計算してみる
- [ ] 普段Excelのピボットテーブルでやっている集計を、SQLのGROUP BYで書き換えてみる

### 第5章: データに「順位」と「文脈」を与える —— ウィンドウ関数入門

**三幕構造:**
- **壁:** 「各部署の売上トップ3」「前月比の増減」をSQLで出せず、Excel関数に逃げている
- **仕組み:** OVER句とPARTITION BY、ROW_NUMBER/RANK/LAG/LEADの基本
- **結果:** 「集合の中の位置」「時系列の前後関係」をSQLで表現できるようになる

**田中さんの課題:**
「各部署の売上トップ3社員を出してほしい」と頼まれた田中。GROUP BYで部署別の合計は出せるようになったが、「各部署の中でのランキング」はどう書けばいいのか分からない。サブクエリでネストして頑張ろうとするが、3段ネストで読めなくなる。

**学ぶ内容:**
1. ウィンドウ関数とは何か —— 「集約はするが、行は潰さない」
2. OVER(PARTITION BY ...) —— グループ内での計算。GROUP BYとの違い
3. ROW_NUMBER / RANK / DENSE_RANK —— 順位をつける3つの方法
4. LAG / LEAD —— 「前の行」「次の行」を参照する。前月比・前年同期比の計算
5. ウィンドウ関数とGROUP BYの使い分け —— 「行を残したいか、潰したいか」

**ストーリーライン:**
「部署別の売上トップ3を出して」と頼まれた田中。GROUP BYで部署別合計は出せるが、「各部署のトップ3」はどう書けばいいのか。サブクエリで試みるが3段ネストで自分でも読めなくなる。佐藤先輩に相談すると「ウィンドウ関数を覚えれば、一発で書けるよ」と教えてくれる。ROW_NUMBER() OVER(PARTITION BY department ORDER BY amount DESC) と書くと、各部署内で売上順に番号が振られ、WHERE rn <= 3 でトップ3が取れる。田中は「GROUP BYは行を"潰す"けど、ウィンドウ関数は行を"残したまま"計算するんですね」と理解する。さらにLAGで「前月の売上」を横に並べ、前月比の増減を計算する体験をする。佐藤先輩は「ウィンドウ関数は"文脈の中のデータ"を見る力。1行のデータを単独で見るのではなく、"その行が集合の中でどこに位置するか"を教えてくれるの」と語る。

**実践ワーク:**
- [ ] ROW_NUMBER() OVER(PARTITION BY ... ORDER BY ...) を使って「グループ内のランキング」を出してみる
- [ ] LAGまたはLEADを使って「前の行との差分」を計算してみる
- [ ] ウィンドウ関数で書いたクエリを、GROUP BY + サブクエリで書き換えてみて、可読性の違いを比較する

### 第6章: SQLを「読む力」—— サブクエリ、CTE、CASE式で複雑なクエリを攻略する

**三幕構造:**
- **壁:** 先輩が書いた複雑なSQLが読めない。サブクエリのネストやCASE式が出てくると手が止まる
- **仕組み:** サブクエリの種類、CTE（WITH句）による分解、CASE式による条件分岐
- **結果:** 複雑なSQLを「部品に分解して読む」スキルを身につけ、自分でも保守可能になる

**田中さんの課題:**
障害対応で先輩が残した分析用SQLを読む必要がある。だがサブクエリが3段ネストし、CASE式で条件分岐が入り、エイリアスが多用されていて全く読めない。修正が必要だが、どこをどう変えればいいか分からない。「読めないSQLは触れない」というボトルネックに直面する。

**学ぶ内容:**
1. サブクエリの種類 —— スカラサブクエリ、テーブルサブクエリ、相関サブクエリ
2. CTE（WITH句）—— サブクエリを名前付きの「部品」に分解して読みやすくする
3. CASE式 —— SQLの中のif文。データの変換・分類に使う
4. 「SQLを読む技術」—— 内側から外側へ、CTEなら上から下へ
5. サブクエリのネストをCTEで書き直す実践 —— 同じ結果、段違いの可読性

**ストーリーライン:**
先輩が残した50行超のSQLを目の前に固まる田中。佐藤先輩は「複雑なSQLは、一気に読もうとするから怖いんだよ。分解して読むの」と語る。まず最も内側のサブクエリから意味を読み取り、外側に向かって1層ずつ理解していくアプローチを教わる。さらに「このサブクエリ、CTEで書き直すと見違えるよ」と言われ、WITH句で名前付きの部品に分解する。50行の難読SQLが、CTEで5つの名前付きブロックに分割され、各ブロックは10行以下の単純なSQLになる。田中は「同じ結果なのに、読みやすさが全然違う...。CTEは"SQLのリファクタリング"ですね」と感動する。CASE式については「通知書の作成と同じ。"ステータスがactiveなら"○"、inactiveなら"×"と表示する"——それがCASE式」と解説される。

**実践ワーク:**
- [ ] 自分のプロジェクトにある「複雑なSQL」を1つ見つけ、最も内側のサブクエリから順に意味を読み取る
- [ ] ネストしたサブクエリをCTE（WITH句）で書き直し、可読性の違いを体感する
- [ ] CASE式を使って「データの分類・変換」を行うクエリを1つ書いてみる

### 第7章: テーブル設計は「世界の切り取り方」—— 正規化とER図

**三幕構造:**
- **壁:** 後輩のテーブル設計レビューを求められたが、正規化の理論が曖昧で自信がない
- **仕組み:** 正規化（第1〜第3正規形）、ER図の読み書き、正規化と非正規化の判断基準
- **結果:** テーブル設計の「なぜ」を理解し、レビューで具体的な根拠を示せるようになる

**田中さんの課題:**
後輩がEC機能のテーブル設計をしてきた。1つのテーブルに「ユーザー名」「住所」「商品名」「商品価格」「注文日」「注文数量」が全部入っている。直感的に「分けた方がいい」と思うが、「なぜ分けるのか」を理論的に説明できない。

**学ぶ内容:**
1. 正規化とは何か —— 「データの重複をなくし、矛盾を防ぐ」設計手法
2. 第1正規形 —— 繰り返しグループの排除。1つのセルに1つの値
3. 第2正規形 —— 部分関数従属の排除。「主キーの一部だけに依存」を分離
4. 第3正規形 —— 推移的関数従属の排除。「キーでないカラム同士の依存」を分離
5. ER図の読み書き —— テーブル間の関係を視覚化する
6. 非正規化の判断基準 —— パフォーマンスのために「あえて冗長にする」場面

**ストーリーライン:**
後輩の「全部入りテーブル」を見た田中。佐藤先輩に相談すると「テーブル設計は"世界の切り取り方"なんだよ」と切り出す。佐藤先輩はホワイトボードに後輩のテーブルを書き、「もしユーザーが引っ越したら？ このテーブルだと注文履歴すべての住所を更新しないといけない。住所は"ユーザー"に属するものであって、"注文"に属するものじゃない」と更新異常の問題を指摘。田中は「なるほど、"何が何に属するか"を考えて分けるんですね」と理解する。佐藤先輩は正規化の各段階を日常比喩で教える。「図書館を想像して。"本の情報"と"貸出の記録"は別の帳簿に書くでしょ？ 本のタイトルが変わったら、貸出帳簿全部を修正するのは大変。だから分ける」。最後にER図を描いて全体の関係を可視化し、「非正規化は"あえて冗長にする設計判断"。理論を理解した上で破るのと、知らずに破るのは全然違う」と締める。

**実践ワーク:**
- [ ] 自分のプロジェクトのテーブル1つを選び、第3正規形を満たしているか確認してみる
- [ ] 「もしこのカラムの値が変わったら、どのテーブルを更新する必要があるか？」を書き出す
- [ ] ER図ツール（draw.io等）で3テーブル以上の関係を図にしてみる

### 第8章: SQLが遅いと言われたら —— EXPLAIN ANALYZEとインデックス

**三幕構造:**
- **壁:** 「このクエリが遅い」と指摘されたが、何が原因か分からない。INDEXを貼る以外の引き出しがない
- **仕組み:** EXPLAIN ANALYZEの読み方、インデックスの仕組みと種類、クエリチューニングの基本
- **結果:** 「遅いクエリ」の原因を自分で特定し、適切な対処法を選べるようになる

**田中さんの課題:**
田中が書いた分析用クエリが「遅すぎる」と指摘された。WHERE句の条件に合うデータは数百件なのに、実行に30秒かかる。「INDEXを貼ればいいんじゃないですか」と言ったところ、佐藤先輩に「INDEXは魔法の杖じゃないよ。まずEXPLAIN ANALYZEで原因を見よう」と諭される。

**学ぶ内容:**
1. EXPLAIN ANALYZEの基本 —— クエリの実行計画を読む
2. Seq Scan vs Index Scan —— テーブル全件走査と索引走査の違い
3. インデックスの仕組み —— 図書館の「索引カード」。B-Treeの基本イメージ
4. インデックスを貼るべき場面・貼るべきでない場面
5. よくある遅いパターンと対処法 —— N+1問題、不要なSELECT *、WHERE句の関数適用

**ストーリーライン:**
「このクエリ、30秒かかるんですけど」と相談する田中。佐藤先輩は「EXPLAIN ANALYZE を付けて実行して」と言う。結果を見ると、Seq Scan（全件走査）が表示されている。佐藤先輩は「図書館で本を探すとき、棚を端から1冊ずつ確認するのがSeq Scan。索引カードから探すのがIndex Scan。数百件の結果を得るために数百万件を全部舐めてたら、そりゃ遅いよね」と説明。適切なカラムにINDEXを作成し、再度EXPLAIN ANALYZEすると実行時間が30秒から0.1秒に。田中は「INDEXってこういう仕組みだったのか...」と感動する。さらに佐藤先輩は「INDEXは万能じゃない。カーディナリティが低いカラム（例: 性別のように値の種類が少ない）にINDEXを貼っても効果が薄い。更新が多いテーブルにINDEXを貼りすぎるとINSERT/UPDATEが遅くなる。"なぜ遅いのか"を理解してから対処するのが鉄則」と念を押す。

**実践ワーク:**
- [ ] 自分のプロジェクトのSQLに EXPLAIN ANALYZE を付けて実行し、Seq Scan / Index Scan を確認する
- [ ] INDEXが効いていないクエリを1つ見つけ、適切なINDEXを作成して実行時間の変化を測定する
- [ ] SELECT * を必要なカラムだけに絞り込み、実行計画の変化を確認する

### 第9章: SQLは50年の「共通言語」—— どのDBでも、どの時代でも

**三幕構造:**
- **壁:** 「PostgreSQL以外のDBでも同じSQLが使えるのか」「この先SQLは必要なのか」という不安
- **仕組み:** SQL標準と各DB方言の関係、SQLの50年の歴史、ORMとの正しい付き合い方
- **結果:** 「SQLはデータベースの共通言語である」と確信し、自分の武器として使い続ける覚悟を持つ

**田中さんの課題:**
SQL力が付いてきた田中だが、「うちのプロジェクトはPostgreSQLだけど、別のプロジェクトはMySQL。前職はOracle。SQLの知識は使い回せるのか？」という疑問が湧く。さらに「AIがSQL書いてくれる時代に、SQL覚える意味あるのか？」という周囲の声も聞こえてくる。

**学ぶ内容:**
1. SQL標準（ISO/IEC 9075）と各DB方言の関係 —— 8割は共通、2割が方言
2. PostgreSQL / MySQL / Oracle / SQLite の違いと共通点
3. ORMとSQLの正しい付き合い方 —— ORMは生産性、SQLは理解と最適化
4. SQLの50年の歴史 —— 1970年のCoddの論文から現在まで
5. 「リレーショナル思考」がもたらす汎用スキル —— BI、データ分析、機械学習前処理にも通じる

**ストーリーライン:**
半年後。田中のSQL力は格段に上がり、障害対応でもデータ分析でもSQLで即座に答えを出せるようになった。高橋部長から「データ分析基盤、よくやったな。他チームにも展開してくれ」と評価される。だが夜、「AIがSQL自動生成」というニュース記事を読み、再び不安がよぎる。佐藤先輩との最後の対話で「SQLの知識がなかったら、AIが出したクエリが正しいかどうかも判断できない。ORMの裏で何が起きてるか理解できない。SQLは1970年にCoddが関係モデルを提唱してから50年以上、データベースの共通言語であり続けている。ツールやDB製品が変わっても、"集合で考える思考法"は変わらない。あなたが身につけたのはSQLの構文じゃなくて、"データの捉え方"なの」と語られる。エピローグで田中は渡辺さんと一緒にマーケ部門向けのSQL勉強会を開いている——「SQLは、エンジニアだけのものじゃないんです」と語る姿がある。

**実践ワーク:**
- [ ] 普段使っているDBとは別のDBの構文を1つ調べ、PostgreSQLとの違いを確認してみる
- [ ] ORMが生成するSQLをログに出力し、「自分ならどう書くか」を考えてみる
- [ ] 自分が書いたSQLの中から「どのDBでも動くもの」と「特定DB依存のもの」を仕分けしてみる

## 7. Killer Phrases（キラーフレーズ候補）10個

1. **「1行ずつ見るな、集合で考えろ。」** —— 本書の核心を一言で表現。Excelの行単位思考からSQLの集合思考へのパラダイムシフト
2. **「JOINは、2冊の帳簿をホチキスで留めること。」** —— JOINの概念を日常比喩で噛み砕く。恐怖を和らげるフレーズ

## 8. Counter Arguments（想定反論と回答）5つ

### 反論1: 「ORMがあればSQL要らないのでは？」

**回答:**
ORMは「簡単なCRUD操作」を効率化する優れたツールである。だがORMは万能ではない。N+1問題の診断、パフォーマンスチューニング、複雑な集計クエリ、障害時のDB直接調査——これらの場面ではSQLの知識が不可欠。さらにORMが「裏で何をやっているか」を理解するためにもSQL力は必要。本書はORMを否定するのではなく、「ORMとSQLの正しい棲み分け」を提案する。ORMで生産性を上げつつ、SQLで理解と最適化を担保する——両方使えるエンジニアが最も強い。

### 反論2: 「AIがSQL書いてくれる時代に、SQL勉強する意味あるの？」

**回答:**
AIが生成したSQLが正しいかどうかを判断するためにも、SQLの知識は必要。「AIが出したクエリを検証できない人」は、AIの誤出力をそのまま本番に適用するリスクを抱える。さらにAIへの指示（プロンプト）の精度は、SQL知識に比例する。「売上の前月比を部署別に出して」と具体的に指示できる人と、「データを分析して」としか言えない人では、AIの出力品質が全く異なる。SQLの知識は「AIを使いこなすための前提知識」であり、AI時代だからこそ重要性が増す。

### 反論3: 「SQL入門書はもう何十冊もあるのに、また新しい本が必要？」

**回答:**
既存のSQL入門書の多くは「構文リファレンス」か「ハンズオン形式のチュートリアル」である。CREATE TABLEから始まり、SELECT/INSERT/UPDATE/DELETEを順に教え、JOINとサブクエリで終わる。本書が描くのは「構文の暗記」ではなく「思考法の転換」。Excelの1行ずつ思考からSQLの集合思考へのパラダイムシフトを、物語形式で追体験させる。田中さんの「ORMに頼りきりでSQLが書けない」悩みは、2026年のエンジニアにとって最もリアルな入口であり、既存書籍のどれも正面から扱っていない切り口である。

### 反論4: 「PostgreSQL中心の内容なら、MySQL/Oracleユーザーには役立たないのでは？」

**回答:**
本書で教えるSQLの8割はSQL標準に準拠しており、どのDB製品でもそのまま使える。SELECT/JOIN/GROUP BY/ウィンドウ関数/CTE/CASE式——これらはPostgreSQL固有の機能ではなく、SQL標準の機能である。PostgreSQLを「実行環境の例」として使うが、概念と思考法はDB製品を問わず通用する。第9章では明示的に各DBの方言と共通点を整理し、「PostgreSQLで学んだSQLはどこでも活きる」ことを示す。

### 反論5: 「物語形式は回りくどい。チートシートだけ端的に教えてほしい」

**回答:**
SQLのチートシートはWeb上に無数にある。だが多くの学習者が挫折するのは「構文が分からない」からではなく「なぜそう書くのか」「どの場面で使うのか」がピンとこないからだ。物語形式は、読者の「感情」（JOINが怖い、サブクエリが読めない、Excelの方が楽）に寄り添い、「自分の現場でもこう使えばいいのか」という具体的なイメージを与える。田中さんシリーズの既刊が証明しているように、物語形式には技術書にない「読了率の高さ」と「行動変容力」がある。

## 9. 差別化ポイント（2026年2月時点の競合分析）

### 競合書籍の状況

**カテゴリ1: SQL入門書**
- 「スッキリわかるSQL入門」（インプレス） —— 初心者向けの定番入門書。構文を体系的に教える教科書スタイル。環境構築からCREATE TABLEまで丁寧だが、物語形式ではなく、「現場でどう使うか」の文脈は薄い
- 「SQL 第2版 ゼロからはじめるデータベース操作」（翔泳社、ミック著） —— 高評価の定番書。丁寧な解説とサンプルだが、やはり教科書形式。ORMとの関係やパフォーマンスチューニングは扱わない
- 「達人に学ぶSQL徹底指南書 第2版」（翔泳社、ミック著） —— 中級者向けの名著。CASE式やウィンドウ関数を深く解説。ただし初心者には敷居が高い

**カテゴリ2: データベース設計・チューニング**
- 「データベース設計の教科書」—— テーブル設計特化。正規化理論を体系的に学べるが、SQL実行スキルとは別の軸
- 「SQLパフォーマンス詳解」—— パフォーマンスチューニング特化。EXPLAIN ANALYZEの深い解説。上級者向け

**カテゴリ3: データ分析のためのSQL**
- 「10年戦えるデータ分析入門」（SBクリエイティブ）—— データ分析視点のSQL入門。非エンジニアにも読みやすいがやや古い
- 「ビッグデータ分析のためのSQL」—— BigQuery/Redshift等のDWH向け。本書とはスコープが異なる

### 本書の差別化ポイント5つ

1. **「物語形式のSQL入門書」は市場にほぼ存在しない**
   - 2026年2月時点で、SQLをテーマにした物語形式の書籍は事実上のブルーオーシャン。「構文の暗記」ではなく「思考法の転換」を物語で追体験させる切り口は独自

2. **「ORMからSQLへ」という現代エンジニアの最もリアルな入口から始まる**
   - 既存書籍はCREATE TABLEから始まるが、2026年のバックエンドエンジニアは「ORMは使えるがSQLは書けない」状態で入門する。この入口から始まる書籍はない

3. **「Excel脳→SQL脳」のパラダイムシフトを正面から扱う**
   - Excelユーザーを読者に含む書籍はあるが、「Excelの思考法とSQLの思考法の根本的な違い」をCore Thesisに据えた書籍はない。非エンジニアにもリーチできる広い裾野

4. **テキスト完結設計でKindle最適化**
   - SQLクエリと結果表だけで完結する。スクリーンショットやGUIの操作手順が不要なため、Kindleの小さな画面でも快適に読める。コードブロックとテーブル表示のみで成立する、SQL書籍ならではの強み

5. **「田中さんシリーズ」のブランド力とクロスセル**
   - 既刊シリーズの読者を自然に誘導できる。Git/GitHub本の読者は「次はSQL」、AI仕事術本の読者は「AIにSQL書かせる前にSQL自体を理解したい」という導線
