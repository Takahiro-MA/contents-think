## 1. Core Thesis（核となる主張）

**「YAMLはもうAIが書ける。だからCI/CDの本当の価値は、"どう書くか"ではなく"どんな環境を選び、どう設計し、なぜそうするか"という判断にある。CI/CDとは、パイプラインの文法ではなく、『動くものを、安全に・繰り返し・自動で届け続ける仕組み』の設計思想である。」**

補足: 本書は「GitHub Actionsの操作マニュアル」ではありません。CI/CDを「1章でざっくり」しか知らなかった田中さんが、実際に1つのプロダクトのCI/CDを**環境選定から設計・構築**し、さらに**環境が根本的に違う現場（閉域・self-hosted）へ異動**して"同じ概念を別の制約下で組み直す"体験を通じて、「CI/CDとは何で、どういう環境が必要で、どう設計するのか」を根本から掴む物語です。AIがYAMLを書ける時代に、人間が握るべき"判断"の部分を学ばせることが目的。田中さんシリーズの縦串（動く→説明できる）の自然な次の一歩＝**「安全に届けられる」**。

## 2. ターゲット読者ペルソナ

### 主ペルソナ: 「CI/CDを"なんとなく"使っているが、根本が分かっていない」エンジニア
- AIエージェント本やチュートリアルで「PR→自動テスト」は見た。YAMLもAIに書かせれば動く。
- だが「そもそもCI/CDとは何で、どういう環境が要り、どう設計するのか」の**全体像（地図）がない**。
- GitHub-hosted runnerと self-hosted runnerの違い、いつどっちを使うか、を説明できない。
- 「分かっているようで、分かっていない」（＝著者自身の実感）。

### 副ペルソナ: 「閉域・オンプレでCI/CDを組まねばならず、クラウド前提の情報が使えない」エンジニア
- 製造業（工場）/自治体/金融など、ネット遮断環境。GitHub Actions×クラウドの記事が前提から通用しない。
- GHES等のオンプレGit、self-hosted runner、外部遮断下のパッケージ/action管理——情報が断片的で体系がない。

## 3. 読者の「具体的な痛み」トップ5

1. **原因不明の失敗を「再実行」でごまかしている**（A-7・日常痛）: たまにCIが落ちるが原因が分からず、再実行（re-run）で通す（flaky）。secrets/permissionでハマってエラーが読めない。CIが遅くて待たされる。うっかりmainを壊して誰かが困る——毎日の泥臭い痛み。※読者が最も"自分のこと"と感じる入口なので、トップに置く。
2. **CI/CDの全体像が霧の中**: 用語（CI/CD/runner/パイプライン/アーティファクト）は聞くが、何がどう繋がるか地図がない。
3. **緑チェックが付けば満足、中で何が起きてるか説明できない**: AIにYAMLは書かせられるが、生成されたパイプラインが妥当か判断できない後ろめたさ。
4. **環境選定ができない**: GitHub-hosted / self-hosted、どれを・なぜ選ぶかの判断軸を持っていない（self-hostedはコスト・速度・特殊環境でクラウド案件でも出る選択肢なのに）。
5. **「動いた」で止まる**: テストは通る。でも本番へどう安全に届けるか（デプロイ戦略・ロールバック）は手つかず。

## 6. ストーリーライン（全9章の物語アーク）

**一文要約**: 「AIにYAMLを書かせれば動く」と思っていた田中さんが、1つのプロダクトのCI/CDを環境選定から設計・構築し、さらに閉域現場への異動で"当たり前だった便利さ"が全部自前になる世界を経験して、「CI/CDとは環境選定と設計判断だ」と掴む物語。

**第1部（基礎・第1〜5章）: クラウド版GitHub × GitHub Actions（GitHub-hosted runner）**
- CI/CDとは何か → 実行環境の全体像（なぜrunnerが要るか）→ パイプライン設計 → デプロイ戦略（本番へ安全に届ける）まで、**インフラの雑音なしに概念を厚く**学ぶ。
- GitHub-hosted runner/marketplace/Secrets/クラウドdeployが"用意されている"世界＝便利さを"当たり前"として体験する。

**第2部（応用・第6〜8章）: 製造業（工場）の閉域現場 —— GHES（オンプレ版GitHub）× self-hosted runner への異動**
- 異動先は**製造業の工場システム**。生産設備・機密情報を守るため工場ネットワークは外部遮断が当たり前。GitHubをクラウドでなく**自社サーバーに設置（GHES）**し、外部ネットから遮断した現場。同じGitHub Actionsなのに、GitHub-hosted runnerが存在しない、marketplaceのactionに繋がらない、Secretsも自前。
- **ツールは同じ（GitHub Actions）、変わるのは"どこで動かすか"だけ＝概念は継承・実装だけ変わる**（「1つの頭・2つの体」）。第1部で学んだ設計思想を、閉域の制約下でどう再実装するか。
- 著者実体験の核＝**本体(GHES)は外部遮断で守り、runnerは別マシンに立てて仕事させる責務分離**、および**外部遮断下でactionをどう調達するか（runnerの限定的外部接続 or 内部ミラー）**という設計判断。
- **クライマックス**: 第1部で"タダ"だと思っていたもの（runnerが湧く/marketplace/Secrets/クラウドdeploy）が、閉域では全部"自前"だと気づく。「便利さの正体を、それが無い環境で初めて理解する」。

**感情アーク**: 「AIに書かせれば余裕」→ 環境選定で詰まる →「動いた」達成 → 本番デプロイの怖さ → 異動で全部通用しない衝撃 →「自前で組み直す」苦闘 →「便利さの正体を理解した」→「CI/CDは環境と設計の判断だ」。

## 8. 構成フォーマットの適応（既存テンプレからの差分）

1. **📘技術解説は「概念＋設計判断」を軸に**: YAMLの文法羅列でなく「なぜこの設計か」「どの環境を選ぶか」を解説（AI時代の価値＝判断、を体現）。具体的なYAMLは要所のみ、原理＋要点で（陳腐化配慮）。
2. **第1部/第2部の"対比表"を効果的に使う**: 「GitHub-hosted（用意されている）vs self-hosted（自前）」の対比を、第2部で繰り返し効かせる（学びのクライマックス装置）。
3. **図版（パイプライン構成図・環境図）を多めに**: CI/CDは構成の可視化が理解を助ける。ただしツールUIの陳腐化に配慮し、原理図中心。
4. **【C-1】IT比喩のドメインを分散させる**: §11は料理系比喩（レシピ/まな板/竈/紙皿/冷蔵庫）に偏りがち。執筆時は料理・建築・交通・軍事・自然などに散らし、「また料理か」を避ける。**感情の山場（1-2の足元が崩れる／6-2の呆然）は比喩なしで感情を優先**、と強弱をつける。例外＝「**山小屋（閉域）** vs 都市（クラウド）」は第2部全体を貫く軸として秀逸なので、第2部で繰り返しブランド化してよい。
5. **【C-3】タイトル「覚える」とテーゼ「暗記不要・判断が主役」の齟齬をまえがきで回収**: 書名は『ストーリーで覚えるCI/CD入門』（シリーズ統一）。まえがきで「**覚えるべきは文法でなく"地図（判断軸）"だ**」と一言回収し、タイトルとテーゼの緊張を武器に転換する。オビ/紹介文は「YAMLはAIが書く。あなたは"読んで判断"できればいい」までハードルを下げ、初学者の購入の最後の一押しにする。

## 9. 差別化

- 競合『GitHub CI/CD実践ガイド』（技評2024・中級ハンズオン/リファレンス）と明確に棲み分け：本書は①**物語形式で初学者に橋渡し**②**AI時代の"設計判断"という時代性**③**実行環境の"地図"**（GitHub-hosted/self-hosted/閉域を判断軸で語る）④**基礎→応用の学習設計**（異動2部構成）。
- 既刊AIエージェント3部作が「CI/CDを1章でざっくり」しか扱わない穴を、丸ごと1冊で埋める。
- **閉域×self-hostedを物語で体系立てて扱う書籍はほぼ皆無**＝独自ポジション。
- **【読者便益への翻訳（A-1）】self-hostedを閉域だけに縛らない。** hostedで困ったとき（コスト・ビルド時間・GPU/特殊環境）の一般解として提示し、「便利さの内訳を知る＝どんな環境でもコスト・トレードオフを判断できる汎用スキル」を第2部の便益にする。閉域はその最も分かりやすい極端ケース。これでクラウド専業読者にも第2部が"自分事"になる。

**「GitHub Actionsに絞る」ことの正当化（＝"ブランドで絞るのは安易"への回答）**
- 「1ツールに絞る」を弱みでなく**教育設計上の意図的判断**として本の中で堂々と語る（第1章冒頭で解消・§11シーン1-1）。これは本書の主題「環境選定と設計判断」と自己相似で綺麗。
- 論拠3点：①**概念と実装の分離**（同じGitHub Actionsを第1部クラウド／第2部閉域で使うから「変わらない概念／変わる環境」がくっきり見える。1ツール固定は異動2部構成の必須条件）②**市場実態**（GitHubが最大シェア＝入門者が最初に出会う。※執筆時再確認）③**深さ優先**（"広く浅く複数ツール"は中途半端＆陳腐化。1つをクラウド→閉域までやり切る深さが価値）。
- **排他しない姿勢を明示**：「GitLab CI/Jenkins/CircleCIも優れた選択肢。本書で得る"判断軸"はどれを選ぶときも効く」→ GitLab派の疎外感を消す。
- **転移可能性を物理的に示す**：主要概念の「GitHub Actions ↔ GitLab CI ↔ Jenkins」対訳を付録に置く（§16）。「学んだ知識は移植可能」を証明＝「1ツールだと潰しが利かない」懸念を潰す。

## 10. 技術正史（全章で守る・ブレ厳禁／執筆時に公式ドキュメント再照合）

> レビュー（技術）で公式照合済み。核テーゼ（GHES air-gasped等）は事実確認OK。ここは執筆チームが守る技術の正。**バージョンで変わる料金・UI・コマンドは執筆時に必ず再照合**。

- **用語の一貫定義**：CI/CD、runner、パイプライン、アーティファクト、ジョブ/ステップ/ワークフロー。
- **AI時代の描き方**：YAMLはAIに書かせられる前提を保ちつつ、"生成物が妥当か判断する"を人間の仕事として描く（「動くけど説明できる」の直系）。**ただし「YAMLを学ばなくていい」と誤読させない**——AIは下書き、人間はレビュー・デバッグできる最低限のリテラシーが要る、という立場を保つ。
- **第1部と第2部の「概念は同じ・実装が変わる」を破らない**（後半を"知識リセット"に見せない）。唯一の例外＝OIDC（完全air-gappedでは外部クラウドとのOIDC連携が原理的に不可＝"前提ごと消える"）を第9章で正直に扱う。
- **GHES正史（公式照合済み）**：GitHub Enterprise Server＝オンプレ設置型GitHub。self-hosted runnerは外部インターネット接続不要でair-gapped運用が公式サポート。本体を外部遮断セグメントに置き、runnerをprivate IP/routingでGHESに接続。**「GitHubはクラウド専用」は誤解**（第6章の学びの核）。
- **【重要・要精密】閉域の外部依存は3層の別問題**（第8章の核）：
  1. **Actions部品** → GHESに `GitHub Connect`（自動取得）または `actions-sync`（手動ミラー）で入れる。**runnerが直接marketplaceに取りに行くのではない**——actionはGHES経由。「本体は遮断・runnerは接続」という責務分離とは"別レイヤー"（混同禁止）。
  2. **ツールキャッシュ**（`actions/setup-*` のNode/Python等バイナリ）→ ネット無しrunnerには手動投入。actions-syncでは解決しない別問題。
  3. **パッケージ依存**（npm/pip/apt/Docker）→ 社内ミラー/プロキシ（Nexus/Artifactory等）。
- **self-hostedは閉域専用ではない**：コスト・ビルド時間・GPU/特殊環境でも選ぶ一般的選択肢（クラウド読者への橋＝A-1）。「self-hosted＝閉域の特殊事情」という誤った地図を渡さない。
- **料金の陳腐化地雷**：2025-2026にself-hosted runner従量課金の発表→撤回、hosted値下げ等の変動。**料金の絶対額は本文に書かない**。self-hosted＝無料前提でコラムを組まない。
- **機能名の接地**：承認ゲート＝GitHub Actionsの **Environments（required reviewers/wait timer）**、マージのゲート＝**ブランチ保護/required status checks（現在Rulesetsへ移行中）**、サードパーティactionは**commit SHA固定**。これら UI名称は変わりやすいので各📘に「執筆時点・最新は公式で確認」の注記を入れる。
- self-hosted runnerの安全：実機ゆえの汚染リスク、**ephemeral化**という緩和策、**publicリポジトリでは使わない**原則。

## 16. 付録: 他ツール対訳（GitHub Actions ↔ GitLab CI ↔ Jenkins）

> **目的（②）**：本書はGitHub Actionsに題材を絞るが、「学ぶのは判断力＝他ツールでも効く」を物理的に示す。主要概念の対応表を付録に置き、GitLab派・Jenkins派の読者に「あなたの知識にも移植できる」と示して疎外感を消す。※各ツールの用語・仕様はバージョンで変わるため執筆時に公式ドキュメントで再照合。

対応表に載せる主要概念（例）：
| 概念 | GitHub Actions | GitLab CI | Jenkins |
|---|---|---|---|
| 設定ファイル | `.github/workflows/*.yml` | `.gitlab-ci.yml` | `Jenkinsfile` |
| 実行環境 | runner（GitHub-hosted / self-hosted） | runner（shared / specific） | agent / node |
| 実行単位 | workflow / job / step | pipeline / stage / job | pipeline / stage / step |
| 秘密情報 | Secrets | CI/CD Variables（masked/protected） | Credentials |
| 成果物受け渡し | artifacts / cache | artifacts / cache | archiveArtifacts / stash |
| 承認ゲート | Environments（required reviewers） | Protected environments / manual job | input step |
| 依存の並列・順序 | needs / matrix | needs / stages / parallel | parallel / stage |

- 付録の位置づけ：「本書の判断軸は、この対訳を介してあなたのツールに持ち帰れる」という一節を添える。網羅リファレンスではなく"移植の橋"として最小限に。
- 執筆時タスク：3ツールの最新用語を公式照合し、概念の粒度を揃える。過剰に細かくしない（陳腐化と分量肥大を避ける）。

### 付録B（C-2）：AI×CI/CDの実務プロンプト集＋レビュー観点チェックリスト
- **目的**：本書のサブタイトル「AIがYAMLを書く時代」の実践版＝物語で腹落ちさせた後の"持ち帰りツール"。購入後の再参照価値（＝レビュー星）を上げる。

- **なぜGitHub Actionsに絞るか**を予告（詳細は第1章）＋他ツールへの敬意（GitLab/Jenkinsも良い選択肢、判断軸は移植できる）。
- 対象読者：「AIにYAMLは書かせられるが、CI/CDの全体像に自信がない人」。

**あとがき（狙い：達成の言語化と次への地図）**
- 田中の到達＝「使える→判断できる」。読者へ「あなたも、次はどんな環境でも、まず地図を広げられる」。
- 「動くだけじゃ、届かない」を回収し、シリーズの縦串（動く→説明できる）に接続。
- 実務への橋：付録のプロンプト集/チェックリスト（§16-付録B）を"持ち帰って"と促す。
