## 1. Core Thesis（核となる主張）

**「YAMLはもうAIが書ける。だからCI/CDの本当の価値は、"どう書くか"ではなく"どんな環境を選び、どう設計し、なぜそうするか"という判断にある。CI/CDとは、パイプラインの文法ではなく、『動くものを、安全に・繰り返し・自動で届け続ける仕組み』の設計思想である。」**

補足: 本書は「GitHub Actionsの操作マニュアル」ではありません。CI/CDを「1章でざっくり」しか知らなかった田中さんが、実際に1つのプロダクトのCI/CDを**環境選定から設計・構築**し、さらに**環境が根本的に違う現場（閉域・self-hosted）へ異動**して"同じ概念を別の制約下で組み直す"体験を通じて、「CI/CDとは何で、どういう環境が必要で、どう設計するのか」を根本から掴む物語です。AIがYAMLを書ける時代に、人間が握るべき"判断"の部分を学ばせることが目的。田中さんシリーズの縦串（動く→説明できる）の自然な次の一歩＝**「安全に届けられる」**。

## 2. ターゲット読者ペルソナ

### 主ペルソナ: 「CI/CDを"なんとなく"使っているが、根本が分かっていない」エンジニア
- AIエージェント本やチュートリアルで「PR→自動テスト」は見た。YAMLもAIに書かせれば動く。
- だが「そもそもCI/CDとは何で、どういう環境が要り、どう設計するのか」の**全体像（地図）がない**。
- GitHub-hosted runnerと self-hosted runnerの違い、いつどっちを使うか、を説明できない。
- 「分かっているようで、分かっていない」（＝著者自身の実感）。

### 副ペルソナ: 「閉域・オンプレでCI/CDを組まねばならず、クラウド前提の情報が使えない」エンジニア
- 製造業（工場）/自治体/金融など、ネット遮断環境。GitHub Actions×クラウドの記事が前提から通用しない。
- GHES等のオンプレGit、self-hosted runner、外部遮断下のパッケージ/action管理——情報が断片的で体系がない。

## 3. 読者の「具体的な痛み」トップ5（骨子・要詳細化）

1. **CI/CDの全体像が霧の中**: 用語（CI/CD/runner/パイプライン/アーティファクト）は聞くが、何がどう繋がるか地図がない。
2. **環境選定ができない**: GitHub-hosted / self-hosted / 閉域、どれを・なぜ選ぶかの判断軸を持っていない。
3. **AIにYAMLは書かせられるが、"設計"は頼めない**: 生成されたパイプラインが妥当か判断できない。
4. **クラウド前提の情報しかない**: 閉域・オンプレだと既存の記事・書籍が通用せず、体系立った情報がない。
5. **「動いた」で止まる**: テストは通る。でも本番へどう安全に届けるか（デプロイ戦略・ロールバック）は手つかず。

## 6. ストーリーライン（全8章の物語アーク）

**一文要約**: 「AIにYAMLを書かせれば動く」と思っていた田中さんが、1つのプロダクトのCI/CDを環境選定から設計・構築し、さらに閉域現場への異動で"当たり前だった便利さ"が全部自前になる世界を経験して、「CI/CDとは環境選定と設計判断だ」と掴む物語。

**第1部（基礎・第1〜5章）: クラウド版GitHub × GitHub Actions（GitHub-hosted runner）**
- CI/CDとは何か → 実行環境の全体像（なぜrunnerが要るか）→ パイプライン設計 → デプロイ戦略（本番へ安全に届ける）まで、**インフラの雑音なしに概念を厚く**学ぶ。
- GitHub-hosted runner/marketplace/Secrets/クラウドdeployが"用意されている"世界＝便利さを"当たり前"として体験する。

**第2部（応用・第6〜8章）: 製造業（工場）の閉域現場 —— GHES（オンプレ版GitHub）× self-hosted runner への異動**
- 異動先は**製造業の工場システム**。生産設備・機密情報を守るため工場ネットワークは外部遮断が当たり前。GitHubをクラウドでなく**自社サーバーに設置（GHES）**し、外部ネットから遮断した現場。同じGitHub Actionsなのに、GitHub-hosted runnerが存在しない、marketplaceのactionに繋がらない、Secretsも自前。
- **ツールは同じ（GitHub Actions）、変わるのは"どこで動かすか"だけ＝概念は継承・実装だけ変わる**（「1つの頭・2つの体」）。第1部で学んだ設計思想を、閉域の制約下でどう再実装するか。
- 著者実体験の核＝**本体(GHES)は外部遮断で守り、runnerは別マシンに立てて仕事させる責務分離**、および**外部遮断下でactionをどう調達するか（runnerの限定的外部接続 or 内部ミラー）**という設計判断。
- **クライマックス**: 第1部で"タダ"だと思っていたもの（runnerが湧く/marketplace/Secrets/クラウドdeploy）が、閉域では全部"自前"だと気づく。「便利さの正体を、それが無い環境で初めて理解する」。

**感情アーク**: 「AIに書かせれば余裕」→ 環境選定で詰まる →「動いた」達成 → 本番デプロイの怖さ → 異動で全部通用しない衝撃 →「自前で組み直す」苦闘 →「便利さの正体を理解した」→「CI/CDは環境と設計の判断だ」。

## 8. 構成フォーマットの適応（既存テンプレからの差分・骨子）

1. **📘技術解説は「概念＋設計判断」を軸に**: YAMLの文法羅列でなく「なぜこの設計か」「どの環境を選ぶか」を解説（AI時代の価値＝判断、を体現）。具体的なYAMLは要所のみ、原理＋要点で（陳腐化配慮）。
2. **第1部/第2部の"対比表"を効果的に使う**: 「GitHub-hosted（用意されている）vs self-hosted（自前）」の対比を、第2部で繰り返し効かせる（学びのクライマックス装置）。
3. **図版（パイプライン構成図・環境図）を多めに**: CI/CDは構成の可視化が理解を助ける。ただしツールUIの陳腐化に配慮し、原理図中心。

## 10. 技術正史（骨子・要詳細化 §12へ）

- 用語の一貫定義（CI/CD、runner、パイプライン、アーティファクト、ジョブ/ステップ/ワークフロー）。
- **公式照合必須**: GitHub Actions構文、self-hosted runner構築手順、GitLab CI、デプロイ戦略の各定義は執筆時に公式ドキュメントで再照合（バージョンで変わる）。
- **AI時代の描き方**: YAMLはAIに書かせられる前提を保ちつつ、"生成物が妥当か判断する"を人間の仕事として描く（田中さんシリーズの「動くけど説明できる」の直系）。
- 第1部と第2部の「概念は同じ・実装が変わる」を破らない（後半を"知識リセット"に見せない）。
- **GHES正史（要公式照合）**: GitHub Enterprise Server＝オンプレ設置型GitHub（GitLab self-managed相当）。self-hosted runnerは外部インターネット接続不要でair-gapped運用が公式サポート。本体を外部遮断セグメントに置き、runnerをprivate IP/routingでGHESに接続。runnerは「GitHub.comのaction自動取得」を無効化すれば完全隔離可。**「GitHubはクラウド専用」は誤解**——この誤解の解消自体が第6章の学びの核。著者実体験のトポロジー（外部遮断本体＋別マシンrunner＝責務分離）はGHESで再現可能。手順・要件は執筆時に公式ドキュメントで再照合。

### 第1部：基礎（クラウド版GitHub × GitHub Actions）

### 第1章: CI/CDって、結局なに？

**シーン1-1：AIに書かせたパイプラインが、静かに壊れていた**
- **場所・時間帯:** 開発室、月曜の午前
- **登場人物:** 田中、山田
- **何が起きるか:** 田中は社内業務Webサービスの開発で、CI/CDを「AIにYAMLを書かせて」設定済みのつもりでした。ところが、あるPRでテストが落ちているのにマージされ、本番で不具合が出ます。調べると、AIが生成したワークフローが「テストの失敗を無視する」設定になっていた。田中は「動いてたのに」と首をかしげます。通りかかった山田さんが画面を覗き、「これ、"動いてる"んじゃなくて"動いてるように見えてた"だけだね」と指摘します。
- **主人公の内心・感情:** 「YAMLはAIが書いてくれたし、緑のチェックも付いてた。なのに、なぜ。……自分は、この仕組みの何を分かっているんだろう」という足元の崩れ。
- **IT比喩:** AI生成YAML＝「レシピは完璧に見えるが、味見をしていない料理」。

**シーン1-2：「CI/CDって、そもそも何を自動化してるの？」**
- **場所・時間帯:** 同、続き（給湯室〜デスク）
- **登場人物:** 田中、山田
- **何が起きるか:** 山田さんが「CI/CDって、そもそも何のためのものか、言える?」と問います。田中は「テストを自動で回す……ええと、デプロイも……」と口ごもる。山田さんは、CI（変更のたびに自動で検証）とCD（検証済みのものを安全に届ける）を、手作業時代の悲劇（「手元では動いた」「リリース手順書の3番を飛ばした」）と対比して説明します。「YAMLはただの"書き方"。大事なのは、何を・なぜ自動化するか、だよ」。
- **主人公の内心・感情:** 「"CI/CDを使ってる"と"CI/CDが分かってる"は、全然違うことだったのか」。
- **IT比喩:** CI/CD＝「工場の検品ラインとベルトコンベア」。作る人の気分に関係なく、同じ品質で流れる。

**シーン1-3：AIがYAMLを書ける時代の、人間の仕事**

- **何が起きるか:** 田中は、GHES本体を外部遮断のまま守りつつ、CIを動かすrunnerをどこに置くか設計します。相沢さんと議論の末、「本体（GHES）は絶対に外に出さない。でもrunnerは、外部のパッケージやツールを取りに行く必要がある」。そこで、本体は遮断セグメント、runnerは限定的に外部接続できる別マシン、という**責務分離**の構成にたどり着く。第1部の「最小権限」「Secretsを守る」思想が、ネットワーク設計として蘇ります。
- **主人公の内心・感情:** 「守るものと、働かせるものを、分ける。これ、第1部の"最小権限"と同じ考え方だ。概念が、環境をまたいで効いてる」。
- **IT比喩:** 責務分離＝「金庫（本体）は奥の部屋に固定し、買い出し係（runner）だけが表に出る」。

**シーン7-2：actionを、どうやって持ち込むか**
- **場所・時間帯:** 同、続き
- **登場人物:** 田中、相沢
- **何が起きるか:** 第1部で当たり前に使っていたmarketplaceのaction（既製の部品）が、閉域では取りに行けません。田中は「あの便利な部品たちが、使えない……」と直面。解決策を2つ検討：runnerに限定的な外部接続を許して取りに行かせるか、必要なactionを内部にミラー（複製して社内に置く）するか。セキュリティと保守性を天秤にかけ、**設計判断**として選ぶ。「YAMLの書き方じゃない。"どう調達するか"の判断だ」。
- **主人公の内心・感情:** 「AIはこの判断をしてくれない。ネットワークの制約と天秤にかけて選ぶのは、人間の仕事だ」。
- **IT比喩:** actionの調達＝「離島でレンガを使いたい。船で毎回運ぶ（外部接続）か、島に窯を作って自前で焼く（内部ミラー）か」。

**シーン7-3：📘 技術解説：self-hosted runnerの構築・維持と閉域の調達戦略**
- **場所・時間帯:** （技術解説の枠）
- **登場人物:** （解説）
- **何が起きるか:** self-hosted runnerの登録・構成、本体遮断＋runner分離のネットワーク設計、外部遮断下でのaction/パッケージ調達（限定接続 vs 内部ミラー/レジストリ）、自前Secrets管理、runnerの維持・更新・セキュリティ（使い捨てでない実機ゆえの汚染リスク）。クラウドで"タダ"だったものの一つひとつに、コストと設計判断があることを体系化。
- **主人公の内心・感情:** （読者と共有）「"用意されている"の中身が、全部見える。便利さの正体を、無い環境で初めて理解した」。
- **IT比喩:** self-hosted runnerの維持＝「使い捨ての紙皿（hosted）と違い、洗って繰り返し使う皿（self-hosted）。割れも汚れも自分で管理する」。

**シーン7-4：☕ コラム：クラウドの"当たり前"の値段**
- **場所・時間帯:** （コラムの枠）
- **登場人物:** （コラム）

- **IT比喩:** クラウドの当たり前＝「蛇口の水。山で沢から引いて初めて、浄水場のありがたみを知る」。

### 第8章: 閉域でCI/CDを完成させる —— そして地図が描けた

**シーン8-1：閉域で、パイプラインが回った**

- **登場人物:** 田中、相沢、山田（リモート助言）
- **何が起きるか:** 自前で立てたrunner、内部調達したaction、自前のSecrets管理、そして閉域内でのデプロイ。試行錯誤の末、工場の生産管理システムのCI/CDが、外部と一切繋がらないまま完走します。第1部で学んだ設計思想（トリガー設計・最小権限・ロールバック・承認ゲート）が、実装は違えど全部息づいている。田中は静かな達成感を噛みしめます。
- **主人公の内心・感情:** 「クラウドとは全然違う組み方なのに、"CI/CDとして"は同じことをやっている。概念は、環境を超えて生きていた」。
- **IT比喩:** なし（応用が結実する瞬間）。

**シーン8-2：環境選定の"判断軸"が、言葉になる**

- **登場人物:** 田中、相沢、山田
- **何が起きるか:** 田中は、クラウド版とGHES、hosted runnerとself-hosted、それぞれを「いつ・なぜ選ぶか」を自分の言葉で整理できるようになっています。相沢さんに逆に説明できるほどに。山田さんが「最初、君は"CI/CDは分かってる"と言ってたよね。今は?」と問う。田中は「あのときは、YAMLが動くのを分かってると勘違いしてた。今は、"どういう環境で、なぜ、どう設計するか"を判断できる。それが分かるってことだったんですね」と答える。
- **主人公の内心・感情:** 「"使える"から"判断できる"へ。CI/CDの地図が、頭の中に描けた」。
- **IT比喩:** 判断軸＝「地図とコンパス。行き先（要件）に応じて、道（環境）を自分で選べる」。

**シーン8-4：振り返り —— 動くだけじゃ、届かなかった**
- **場所・時間帯:** 工場からの帰り道／自宅、夜
- **登場人物:** 田中（内省）、山田（回想）
- **何が起きるか:** 田中は、第1章で「AIに書かせれば動く」と思っていた自分を思い返します。あのときは"動く"のゴールしか見ていなかった。今は、"動く"の先に「安全に届ける」「どこで動かすか選ぶ」「なぜそう設計するか説明する」があると分かる。AIがYAMLを書く時代に、自分が本当に身につけたのは、文法ではなく判断だった——と腑に落ちる。次のプロジェクトでは、どんな環境でも、まず地図を広げられる。
- **主人公の内心・感情:** 「"動くだけじゃ、届かない"。CI/CDは、動かす技術じゃなくて、安全に届け続けるための設計思想だった」。
