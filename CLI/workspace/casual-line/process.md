# カジュアルライン 書籍制作プロセス

> C01『AIの始め方、これだけでOK』（2026-09）の制作で実際に回したプロセスを、次の本でも同じ手順で回せるようにまとめたもの。
> シリーズの方針（価格・品質フロア・タイトルの型）は `series-charter.md`、各巻の企画は `concepts/`、
> 日付つきの決定記録は `notes/` を正とする。本書は「どう作るか」の手順書。
> 参照実装: `../kindle2/C01_ai-left-behind/`（出版準備まで完了した最初の1冊。量産時はこのフォルダ構成と `build/` を複製して使う）

## 0. 役割分担

| 担当 | やること |
|---|---|
| 著者 | 企画の方向づけ、コンセプトと原稿の違和感指摘、体験の事実確認、タイトル・ペンネーム・表紙の最終決定、KDP登録 |
| Claude（親） | 進行管理、判断材料の整理、サブエージェントへの指示と結果の検証、小さな修正、コミット |
| サブエージェント | 調査・執筆・一括修正・画像作成・ビルド改修（原則 Sonnet、文章の質や判断が要るものは Opus） |

- サブエージェントの報告は必ず実物で検証する（ファイル・ビルド・画像を開いて確認）。報告だけで完了にしない
- 反映は「指摘を溜めて一括」が基本。著者が「反映は後で」と言ったら `review-notes.md` に積むだけにする

## A. 企画・コンセプト

1. 題材はシリーズの主旨（始めるハードルは思っているより低い）に合うものを選ぶ
2. コンセプト文書を Claude が書き切り、著者は赤入れだけする。含める項目:
   - 中核主張（タイトルが回収すべき約束）と「この本が教えないこと」の宣言
   - ターゲット読者（現在地・つまずきの正体・読後の状態）
   - なぜ今か
   - 章構成（各章の役割を1〜2行）と章末Q&Aの有無
   - トーンサンプル（書き出し数行。わざとらしさの判定用）
   - 道具の名指し方針（ブランドは特定の枠に隔離し、本文は総称で書く）
   - 執筆時に事実照合が必要な項目
3. 著者の観点: 違和感・わざとらしさ・不足。構成の指摘（例: 「疑問に答える要素が足りない」「使って終わりでなく広がりが欲しい」）はここで吸収する
4. **体験談スロットは作らない**。プレースホルダー方式は著者に「わざとらしい」と却下された（2026-09-25）。体験は、著者レビューで本人が出したものだけを後から入れる

## B. 事実パック（執筆前）

- 本文に出る数字・サービス仕様を、執筆前にサブエージェントで集める。公的統計（総務省の白書等）を優先し、民間調査は調査条件ごと記録する
- 執筆指示に「この一覧以外の数字は使用禁止」として埋め込む（捏造数字の構造的防止）
- 収集結果で企画の前提が崩れたら、著者に伝えて論旨を組み替える（C01では利用率が58.8%に急伸しており、「未利用は多数派」から「半分が使い始めたから焦る、でも今から始める人は珍しくない」に変更）

## C. 一括執筆

- Opus のサブエージェント1体に全章を書かせる（声の一貫性のため分割しない）
- 指示に含めるもの: コンセプトとシリーズ憲章のパス、事実パック、文体ルール（ですます・専門用語の禁止リスト・AIっぽさの禁止事項）、ファイル構成、完了条件
- 完了条件の例: 全ファイルあり／文字数±15%／事実パック外の数字なし／禁止語ゼロ

## D. 初回レビュー（1周）

- P1 事実・約束違反 → P2 文体 → P3 構成 の順でサブエージェントに見させる。数字はウェブで独立照合させる
- 軽微な指摘はその場で直してコミット

## E. ビルド環境（EPUB）

- **markdown が唯一の真実源**。XHTMLやEPUBを手で直さない。直すときは md を直して再ビルド
- 雛形は既刊EPUB（C01は `~/worldwide/kiro-cli/source/KiroCLI.epub`）を解剖して `build/template/` に部品化
- `build/build_epub.py` の機能:
  - md → XHTML（見出し・段落・太字・箇条書き・複数行の引用・単独行の画像 `![キャプション](images/x.png)`）
  - `images/` を自動で取り込み、目次・OPFを生成、epubcheck を実行
  - 章リスト（`CHAPTER_FILES`）に漏れた md があるとエラーで止まる
  - **版番号付きで出力**: `release/<slug>_vNN_YYYYMMDD.epub`。Kindle上で見分けられるよう書名にも `[vNN MM/DD]` を付ける。出版用は `--final` で印なし
- CSS はWeb組版（字下げなし・段落間の余白・行間1.9）。カジュアルラインの読者向け
- 著者への受け渡し: `SendUserFile` でEPUBを送り、スマホで「共有→Kindle」。Gmail 経由の自動送信は添付をbase64で流す必要があり重すぎるため使っていない（アプリパスワード方式のSMTP送信は未導入）

## F. 著者レビューの反復

- 指摘は `review-notes.md` に番号付きで溜め、「反映して」で一括反映 → ビルド → epubcheck → コミット → EPUB送付
- C01で実際に効いた修正の型:
  - **組版**: 段落を1〜3文に切り直す（文字は1文字も変えず、空白を除いた本文の一致を機械検証）
  - **専門用語**: 初出で出さない。使うなら一言で言い換えを添える（サブタイトルも対象）
  - **事実が古い記述**: AIサービスの仕様は数か月で変わる（会話の記憶、サインイン要否、名称変更）
  - **AIっぽさの監査**: 別エージェントに全文を監査させ `ai-ism-audit.md` に出させてから一括修正。主因は ①短文の決め台詞で節を締める ②慰め・許可の言葉の多用 ③「AではなくB」と根拠のない数字の言い切り。**決め台詞を独立段落にする組版指示は逆効果だった**
  - **削除後の継ぎ目**: まとめて削った後は、指示語の受け先・章参照・取り残された段落を全文で点検する
  - **体験の記述**: 著者の体験として書かれている箇所を列挙し、一つずつ事実か確認する。確認できないものは削る
  - **前書き**: 対象読者（誰向け・誰には物足りないか）を冒頭で明記する。期待値のずれは低評価の最大要因
- 著者から出た方向の指摘は原則「直す方向」で受ける

## G. 画像

- **画面キャプチャ**: Playwright（`npx playwright`、Chromium）でスマホ幅を再現して撮る
  - `--device="Pixel 7" --lang="ja-JP" --timezone="Asia/Tokyo"`。WebKit系（iPhone）は未導入
  - 撮影前にバナー類を閉じる。撮影後にPILで切り抜き・赤枠・ラベルを付ける（画面の中身は書き換えない）
  - ログイン後の画面とアプリ内の画面は撮れない（著者のスクショで補う）
- **実際のやりとりの記録**: ログイン不要のサービスに実際に送って返事を取得し、本文にそのまま載せる。完了判定は「生成停止ボタンが消える」で行う（テキストの変化が止まるだけでは誤判定する）
  - ChatGPT: 入力欄 `#mobile-composer-prompt`、返事 `li[data-message-role="assistant"]`、生成中は `aria-label="生成を中止する"`
- **生成画像**: Codex CLI（サブスク枠内）。`cd /tmp && codex exec --skip-git-repo-check "Generate ONE image using your image generation tool: <プロンプト>" </dev/null` → `~/.codex/generated_images/` の最新ディレクトリから回収
  - 実行後にシェルのcwdがリセットされる。以降は絶対パスで
  - サブエージェントが生成完了に気づかず待ち続けることがある。親が出力ディレクトリを Monitor で見張り、止まったら指示する

## H. 出版前の事実照合

- 全文から検証可能な記述を抽出し、公式・一次ソースで照合して `factcheck-YYYY-MM-DD.md` に表で残す
- **根拠は原文の引用で**。要約ツールの言い換えを原文と取り違えた事例あり（Copilot「サインインは任意」、2026-09-27）
- **別サービスとの混同に注意**。「LINEのAIは1日3回」の根拠が別サービス（AIチャットくん）の記事だった。実際は「LINE AI」が2026-04-20に「Agent i」へ統合されていた（2026-09-28）
- 数字が公式で確認できないものは本文に書かない

## I. タイトル

- **KDPは出版後にタイトルを変更できない**（誤字修正のみ。変えるなら新しい本として出し直し）。一発勝負として扱う
- 手順:
  1. 型ごとに候補を広げる（超入門型・心の声型・読者を絞る型・数字型・安心型・条件型・年齢型・結果型・逆説型・直球型など）。外部AI（ChatGPT等）の案も候補プールに入れる
  2. **必須条件でふるう**: メインタイトルだけで何の本か分かる／中身と一致する／誇大・最上級・価格・他社商標を含まない
  3. 残りを「指が止まる」「検索に当たる」「重ならない」で採点
  4. 上位案を Playwright で Amazon.co.jp 実測（完全一致・類似書名・検索窓の候補語）。C01では有力候補『今さら聞けないAIの始め方』が同名既刊ありで脱落
  5. **表紙に載せて比べる**。文字だけで決めたタイトルが、表紙で見ると印象が変わることがある
- サブタイトルには実際に検索される語（例: 「生成AI 初心者」）を入れ、残りの検索語はKDPのキーワード欄7つで補う
- 「いちばんやさしい」はインプレスのシリーズ名と重なり、最上級表現でもあるので使わない
- **句読点は表紙で見て決める**。C01は『これだけでOK。』→『これだけでOK』に変更。末尾の「。」を外しただけで表紙の印象が軽く強くなった（2026-09-28）。表紙の書名とKDP登録の書名は一致させる
- C01の経過: 型で広げる → 必須条件ふるい → 採点・Amazon実測 → 一度決めた案（これだけでOK）を表紙に載せて他案と比較 → 結局元の案に戻した。**タイトル単体の迷いは、多くの場合「表紙の出来」の問題**だった

## J. 表紙

- 最初に**売れ筋の表紙を30〜50冊集めて型を抽出する**（Playwrightで検索上位と売れ筋ランキングから取得、一覧画像と75px幅の比較画像を作る）。C01の調査結果: `../kindle2/C01_ai-left-behind/cover-research/patterns.md`
- 数値基準: 書名が表紙の35%以上（33%を下限）／Amazon検索結果の約75px幅で書名が読める
- **文字と絵を一体で作る**。絵だけ生成して後から文字を重ねる方式は「素人くさい」と却下された。Codexに文字込みで生成させ、全文字を拡大して一字ずつ照合する（誤字があれば再生成）
- サイズ 1600×2560px、RGB、JPEG
- 表紙に使わないもの: 他社商標、実在サービスのロゴ・画面、実績表示（No.1、〇万部）、価格、根拠のない最上級、本文から外した専門用語
- 帯のコピーは本文に書いてある事実だけで作る
- 候補は並べて見比べる（型ごとに1案ずつ → 選んだ型を調整 → 必要ならタイトル差し替え版）
- **表紙の文字の大きさは4段階の強弱で指定する**: ①書名の決め語（C01なら「OK」、書名の横幅の3分の2ほど） ②書名の残り ③帯の大きなキャッチ ④サブタイトル・札・帯の補足・著者名（小さく控えめ）。「全部大きく」はテンプレート感の原因
- **赤丸・シールの中身は「買う理由になる事実」にする**。「声と写真でもOK」は弱いと却下。「疑問にぜんぶ答えます」（第3章の章題と同じ言葉）を採用
- **一部の色だけ変えたいときは作り直さない**。作り直すと全体の配置が変わる。PILで対象の文字だけ塗り替える（背景色と文字色から輪郭の濃さを求めて色を置き換え、なめらかさを保つ）。C01では書名の「AI」を紺→赤にした
- C01で比べた他の手段と結果（2026-09-28）:
  - 絵だけ生成して文字を重ねる → 素人くさい（却下）
  - Canva MCP（`create-design`、形式「Book Cover」1410×2250が通る） → 字組みは洗練されているが地味で、売れ筋の棚では埋もれる。部品ごとの編集と著者の手直しができるのは利点
  - Codex CLI の更新（0.147→0.158） → 同じプロンプトで仕上がりはほぼ同じ。画像モデルはサーバー側で、CLIの版では変わらない
- 採用した表紙は `<book>/cover/cover.jpg` に置く。ビルドが自動でEPUBの表紙に組み込む（無ければ仮の表紙を生成）
- 表紙は出版後もKDPで差し替えられる（タイトルと違い一発勝負ではない）。迷ったら出して、あとで良くする

## K. 出版準備

- サブエージェント（Opus）1体に一式を作らせ、`<book>/publish/` に出す。作るもの:
  - `description.md`: 商品説明文（HTMLなし、600〜1000字）。対象読者と「誰には物足りないか」を必ず明記（前書きと揃える）。タイトルの約束を広げない
  - `keywords.md`: KDPキーワード7つとカテゴリ候補。**Amazon検索窓の候補を実測して裏づける**（Playwrightで検索カテゴリを「Kindleストア」にして1文字ずつ入力し、候補を取得。生データは `publish/data/` に保存）。**他社のサービス名はキーワードに入れない**（KDP公式が「所有していない、または使用が許可されていないブランド」を避けるべきとしている）
  - `compliance-check.md`: タイトル・表紙の全文言・説明文・キーワード・本文の画面キャプチャを、景品表示法・商標・著作権・KDPガイドラインで点検（根拠は原文とURL）
  - `kdp-entry-sheet.md`: KDP登録画面（詳細／コンテンツ／価格設定）の項目を上から順に、何を入れるか一覧にしたもの。AI利用申告の答え方も入れる
- 出版用EPUB: `python3 build_epub.py --final` → `release/<slug>_final.epub`。書名の版の印が外れ、更新日時が実際の値になる。識別子は同じ本で一定のまま（EPUBの仕様で、小さな改訂では変えない）
- 著者が決めること（入力一覧に印をつける）: ペンネームの読み、AI申告の「編集の程度」、年代語をキーワードに入れるか、DRM、海外価格の手直し
- **海外価格**: 299円を自動換算すると、国によっては70%ロイヤリティの最低価格（米国$2.99）を下回る。登録画面で範囲外と出た国は手で直す
- **AI利用申告**: KDPの定義では、Claudeが書いた本文もCodexの表紙も「AI生成」に当たる。設問の正確な文言はログイン後の画面にしかない
- **コンプライアンス指摘への著者判断（C01）**: 画面キャプチャの出典表記・他社ロゴが写った画面の削除・商標注記は「反映しない」と判断（2026-09-29）。EPUBは出版後に差し替えられるので、指摘を受けたらその時点で直す。次の本では、**他社のロゴが写る画面（サインイン画面など）はそもそも使わない**ほうが手戻りがない
- **紙の本は出さない（Kindleのみ）**（2026-09-29方針）: 2万字台だと80〜100ページになり、1,000円未満は紙のロイヤリティ50%で印刷代を引くと利益がほぼ残らない。画面キャプチャが白黒になる。印刷用PDFと背表紙つきの表紙の作業が別に要る。売れ行きとレビューで紙の需要が見えたら、その本だけ追加する
- 著者がKDPに登録して出版したら、`CLI/workspace/book-status.md` のカジュアルライン節を「出版済み」に更新する

## 新しい本の立ち上げ（量産時の手順）

1. `concepts/NN-<slug>.md` を書く（A工程）。番号はシリーズ通し番号
2. `../kindle2/CNN_<slug>/` を作り、C01から次を複製する: `build/`（`build/work/` は除く）、`review-notes.md` の見出しだけ
3. `build/build_epub.py` の定数を書き換える: `BOOK_SLUG`、`TITLE`（仮題でよい）、`AUTHOR`（高木 崇英）、`CHAPTER_FILES`（章数に合わせる。漏れがあるとビルドが止まる）
4. `epub/` に原稿、`images/` に画像、`cover/cover.jpg` に表紙を置く。あとはB〜K工程の順に進める
5. 1冊ごとに `CLI/workspace/book-status.md` のカジュアルライン節に行を足し、状態を更新する
