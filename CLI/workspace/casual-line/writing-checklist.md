# カジュアルライン 執筆前チェックリスト

> C01の著者指摘23件（`../kindle2/C01_ai-left-behind/review-notes.md`）とAIっぽさ監査から作った、次の本で最初から守る決まり。
> 使い方: 企画（A工程）と執筆（C工程）の指示にこのファイルを必ず渡す。初回レビュー（D工程）では、この項目に沿って点検させる。
> 括弧内は元になったC01の指摘番号。新しい指摘が出たら、ここに追記する。

---

## 1. 企画・構成

- [ ] **読者がその本を買う動機を先に確かめる**。「始めるハードルを下げる」はC01（AIに乗り遅れた人）の読者の動機に合った型で、全テーマに当てはまるわけではない。体を変えたい人には、変わる方向（成果）を見せる（C02の著者指摘、2026-09-29）
- [ ] 成果の目標は、読者ごとに意味が変わる絶対値（−2kg等）ではなく、方向（ベクトル）と自分比で示す（C02）
- [ ] 冒頭で**誰のための本か、誰には物足りないか**を明記する構成にする。期待とのずれは低評価の一番の原因（#17）
- [ ] 読者の「始める前の疑問」に答える章か節がある。各章末に読者の内心の不安を1〜2問、Q&Aで置く（企画段階の指摘）
- [ ] 「言われたとおりにやって、おしまい」で終わらせない。最後は読者が自分で広げられる方向を示す。ただし難易度は上げない（企画段階の指摘）
- [ ] 最終章は、読者が本当に欲しい方向か確かめる。書き手の理想（例: 他人に教える側に回ろう）を押しつけない（#9）
- [ ] 章数は中身で決める。区切りのよさ（10章など）のために薄い章を足さない
- [ ] 具体例を一つのサービス・一つの題材でやり通す章を作る。「どれでもいい」だけでは読者が動けない（#13）

## 2. 事実と体験

- [ ] **体験の穴埋め欄（プレースホルダー）を作らない**。体験は、著者が自分から出したものだけを後から入れる（体験スロット削除）
- [ ] 著者の体験として書く文は、書いた時点で一覧にし、著者に事実か確認する。確認できないものは書かない（#16・#17・#18・#22）
- [ ] 「まわりで何度も聞いた」「みなさん〜していました」のような、作った場面の描写をしない（#16・#17）
- [ ] 数字は事実パックにあるものだけ。「一週間で慣れる」「差は一、二分」のような、根拠のない数字や言い切りを書かない（#20）
- [ ] 変わりやすいサービスの仕様（ログインの要否、無料の回数、会話の記憶、名称）は、**執筆の直前に公式で確かめる**。数か月で変わる（#6・#12・#19）
- [ ] 公式で数字を確認できないものは、数字を書かずに「制限がある」とだけ書く（#19）
- [ ] AIの弱点（間違い、情報の扱い）は、今の実態に合った頻度で書く。怖がらせすぎない（#10）
- [ ] 「改善に使われる」「学習される」のような抽象語は、何が起きるか（保存される、人が読むこともある）で書く（#4・#8）

## 3. 言葉

- [ ] **専門用語を初見で出さない**。タイトル・サブタイトル・帯も対象。使うなら、初めて出たところで一言言い換える（#2）
- [ ] カタカナ語は3つに分けて扱う: 日常語に置き換える／初出で一言説明して残す／読者の日常語なのでそのまま（LINE・スマホ・アプリ等）（#2）
- [ ] 仕事の話では、主語を読者にそろえる。機密情報（社外秘・取引先名・個人情報）を入れない注意を必ず書く（#15）

## 4. AIっぽさを出さない

- [ ] **短い一文だけの段落で節を締めない**（決め台詞）。節は情報の文で終える（#20）
- [ ] 「急かしません」「〜はあなたが決めてください」のような、過剰に優しい語りかけや詩的な締めをしない（#20）
- [ ] 慰め・許可の言葉（〜なくていい／かまいません／十分です／大丈夫です）は1章2回程度まで（#20）
- [ ] 「AではなくB」の言い換えは、本の中心の主張以外では使わない（#20）
- [ ] 同じ宣言・同じ比喩を何度も繰り返さない。まえがきと最終章で同じ台詞を使う円環構造にしない（#20）
- [ ] 「〜のです」「つまり」「むしろ」を連発しない（#20）
- [ ] 章の書き出しと締めが、全章で同じ形にならないようにする（#20）

## 5. 組版・見た目

- [ ] 段落は1〜3文。note・ブログの丁寧な書き手くらいの改行（#23）
- [ ] 例や選択肢が3つ以上並ぶところは、文章に埋めずに箇条書きにする（#7）
- [ ] 行間はCSSで1.9（C01のビルド設定をそのまま使う）（#1）
- [ ] 操作の説明には、実際の画面の画像を入れる。ボタンの位置は赤枠やラベルで示す（#3・#13・#14）
- [ ] 他社のロゴが写る画面（サインイン画面など）は使わない（出版前の点検で指摘）
- [ ] 本文で「実際に送ってみました」と書くときは、本当に送った記録を載せる。要約で済ませない（#5）
- [ ] 同じ相談を別のサービスで見せるときは、別のサービスだと本文に書く（#19）

## 6. 直したあと

- [ ] まとめて削ったあとは、全文でつながりを点検する: 受ける先が消えた「その」「それ」、急に始まる話題、今の構成と合わない「第◯章で書いたとおり」（#21）
- [ ] 章を足したり削ったりしたら、ビルドの章リスト・まえがきの読み方案内・章をまたぐ参照を直す（#9、第10章の抜け）

## 7. 書誌・表紙（出版準備の工程で確認）

- [ ] タイトルの句読点は、表紙に載せて見て決める（C01は末尾の「。」を外した）
- [ ] 表紙の赤丸・シールには、買う理由になる事実を入れる（「声と写真でもOK」は弱いと却下）
- [ ] KDP入力の固定ルール（書名・サブタイトル・著者のフリガナとローマ字、出版社、キーワード7枠×複数語）は `process.md` のK節に従う
