## 2.5 Kiro IDE と Kiro CLI の整理（本書がCLI主軸を選ぶ根拠）

### 共有しているもの（IDEもCLIも同じ）
- **Specs**（`requirements.md` / `design.md` / `tasks.md`）
- **Steering files**（プロジェクト方針ファイル）
- **MCP統合**（外部ツール接続）
- **モデル**（Claude Sonnet 4.5 / Haiku 4.5 / Auto）
- **サブスク・認証**（共通アカウントでcredit共有）
- **Custom agents**

### 違うもの

| 項目 | Kiro IDE | Kiro CLI |
|------|----------|----------|
| UI | GUI（VS Code系） | ターミナル |
| 操作の基本 | パネル・タブ・クリック | コマンド・パイプ・stdin/stdout |
| Specs作成UI | パネルで対話的に | 近日対応（既存specの利用は可） |
| **Headlessモード** | × | **○（CI/CD組み込み可）** |
| Hooks | Hooks（ファイル操作トリガー） | **Smart Hooks（pre/postコマンド）** |
| AWS CLI連携 | △ | **○（自然言語でAWS操作）** |
| 環境依存 | GUI必須 | SSH／コンテナ／CIで同じ動作 |

### なぜAIエージェントにCLIが向いているのか（構造的理由7つ）

「気のせい」「単なる好み」ではなく、客観的に成立する理由：

1. **コンテキストが明示的** — `cd`/`cat`/`ls` で「何を見せ、何を見せないか」を統制できる。IDEは開いているタブ・カーソル位置などの暗黙コンテキストがノイズになる
2. **状態モデルが単純** — CLIはstdin/stdout/stderr/exit code/ファイルの少数次元。IDEはエディタ・パネル・デバッガなど多次元
3. **ReActループとの相性** — Think→Act→Observe→Thinkの一回が明確に区切られる。IDEはリアルタイムサジェストが境界を曖昧にする
4. **Unix哲学に乗れる** — shell/pipe/grep/git等の既存ツールと素直に組み合わさる
5. **環境の純粋性・移植性** — ローカル／SSH／Docker／CIで同じ挙動
6. **自動化が自然** — そのままスクリプト化・headless実行・CI組み込み可能
7. **テキストI/O中心 = LLMの素性と一致** — LLMは本質的にテキスト処理機、CLIもテキストI/Oが本籍

### 主観・好み由来の理由3つ（こちらも気のせいではない）

8. **「自分の道具」感** — 自分のシェル/エディタ/dotfilesにエージェントが乗ってくる
9. **コントロール感** — 一行ずつ承認、exit codeで結果確認、historyで履歴追跡 → 掌握感
10. **キャリア背景** — ターミナル中心の作業習慣がある人には素直に速い

### IDEが優位な場面（バランスのため記録）

- ビジュアル中心の開発（フロントエンド、デザイン、UI実装）
- 大規模リファクタリングで複数ファイルを並行表示したい
- デバッガとの密統合が必要
- 初心者の学習導線（CLIは敷居が高い）
- チーム内で全員がターミナルに慣れているとは限らない

→ KiroがIDE/CLI両対応で共通設定（Specs・Steering・MCP）にしている理由はここ。本書もIDEを完全否定はしない。

### 本書での扱い方
- **第1章付近**：田中さんが「IDE版もあるけど、CLIにする」を選ぶシーンで、構造的理由を主人公の言葉で言語化
- **神谷さん（PdM）との対話**：神谷は最初「IDEのほうが見やすそう」と言う → 田中が「AIエージェントとの相性で言うと…」と説明 → 議論を経て **「Specsは共通、運用はCLI主軸」** で合意する流れ
- IDE版に触れる際は「否定」ではなく「適材適所」のトーンで

## 4. 「Kiroを外向き製品開発に使う」懸念の取り込み

### 攻めの方針
3つの懸念をすべて物語に取り込み、**採用判断プロセス自体を本書の独自価値にする**：

1. **開発ツールとして使う妥当性** — Cursor/Copilot系と同じ問題系。Spec workflowは監査証跡として有利
2. **インフラ依存** — Kiroは開発IDE/CLIであって、生成物の本番動作はKiroに依存しない
3. **機密漏洩** — Enterprise: データ非保存、KMS、IAM Identity Center／Okta／Entra連携、モデル・MCP制御

### 取り込みポイント
- **第1章付近**: 神谷さんが「Kiro使う？」と問題提起
- **どこかで**: 個人プラン vs Enterpriseプランの違い
- **どこかで**: 2025-12 のKiro/AWS Cost Explorer本番削除インシデント（自律判断＋人間承認バイパスが原因）に自然に触れ、**安全運用ルール**（PreToolUse Hookによる人間承認必須化、権限の最小化、監査ログ強制）を整備する章

### 期待される独自価値
入門書を超えて、**「外向きプロダクト開発でAIエージェントを採用する判断書」** としても機能する。

- **テーマ**: PoCの「頭の中にあった仕様」を文書として外化する

- **扱う技術**: Kiro Specs 3段階の概要、requirements.md の書き方、ユーザーストーリー、受け入れ基準
- **感情**: 戸惑い → 発見 → 達成感
- **神谷関係**: 神谷の知識（自治体現場感）が田中に流れ込む
- **コラム候補**: 「Specs と CLAUDE.md／AGENTS.md の違い」
- **読者の痛み**: PoCの後の仕様文書化が苦痛、何を書けばいいか分からない

### 第3章：「設計、どこに書いてました？」── design.md でアーキテクチャを描く
- **テーマ**: 設計の文書化＝「説明可能」への昇格
- **シーン**: 神谷「design.md ある？」 → Kiroとアーキテクチャ議論 → マルチチャネル（LINE/Web/電話）統合設計 → 監査ログ層・セキュリティ層の追加（神谷の自治体経験が活きる）→ AI出力の確信度判定とエスカレーション
- **扱う技術**: design.md の書き方、AWS構成（Bedrock・Lambda・API Gateway・KMS・CloudWatch）、マルチチャネル統合、監査ログ・改ざん検知の設計
- **感情**: 抵抗 → 理解 → 納得
- **神谷関係**: 神谷の自治体経験が「現場のリアル」として田中に入る
- **コラム候補**: 「自治体システムにおける『説明責任』」
- **読者の痛み**: 設計書を書く意義が分からない、AWS構成図の描き方が分からない

### 第4章：「タスクが見えると、進められる」── tasks.md と Subagents で実装の波を作る
- **テーマ**: 設計から実装計画への落とし込み、並列実行の体感
- **シーン**: tasks.md の作成（design.md から分解）→ 依存関係の整理（タスクグラフ）→ Subagents で並列実行 → 並列で進む実装をモニタリング・レビュー → PoCコードの再利用判断（捨てる／活かす）
- **扱う技術**: tasks.md の書き方、Subagents（依存解析つき並列実行）、田中×Kiroの実装プロセス、PoCコードのリファクタリング判断
- **感情**: 半信半疑 → 驚き → 確信
- **神谷関係**: 神谷は田中の実装をレビューする側へ、相互信頼の構築
- **コラム候補**: 「並列実行は本当に速い？ Subagents の依存解析を覗いてみる」
- **読者の痛み**: 実装スピードを上げたい、複数機能の同時実装が苦手

### 第5章：「日々の運用、人がやらなくていい」── Hooks で開発フローを仕組み化
- **テーマ**: 日常の繰り返し作業を Kiro に任せる、ただし安全に
- **シーン**: PoC期の「忘れがちな後始末」の振り返り → Hooks の概念学習（pre/postコマンド）→ ゴミ分別データ更新時の自動再インデックス → テストとドキュメントの自動更新 → **2026-03 Kiro/AWS インシデントへの言及、安全な権限設計議論**
- **扱う技術**: Hooks、ファイル保存／コミット時の自動処理、権限制限・サンドボックス、監査ログとの統合
- **感情**: 面倒さ → 気づき → 解放感（からの安全への気引き締め）
- **神谷関係**: 神谷が「自動化と監査の両立」を提案、田中が実装
- **コラム候補**: 「AIエージェントの暴走をどう防ぐか ── 2026年3月の事件から学ぶ」
- **読者の痛み**: 日々の運用作業が辛い、AIに任せて大丈夫？

### 第6章：「チームの『当たり前』を、文書にする」── Steering でプロジェクト方針を統一
- **テーマ**: チーム規約の言語化、AI出力の品質保証
- **シーン**: AI回答の口調がチームメンバーごとに違うことに気づく → Steering ファイルの作成 → 引用元明示、不確実な内容の禁止、表現統一ルール → レビュー文化の確立 → 神谷との「チームでの基準作り」議論
- **扱う技術**: Steering の書き方、プロジェクト方針の文書化、AI出力の品質保証、チームレビューフロー
- **感情**: 些細な違和感 → 重要性発見 → 共有の喜び
- **神谷関係**: 協働関係が完全に確立、田中の側が神谷に提案できるレベルへ
- **コラム候補**: 「Steering / CLAUDE.md / AGENTS.md ── 3つの『プロジェクト統制』を比べる」
- **読者の痛み**: チーム内のAI利用がバラバラ、品質統一が難しい

### 第7章：「動いてるだけじゃ、もう足りない」── Headless モードで CI/CD に組み込む
- **テーマ**: リリース前検証の自動化、説明責任の仕組み化
- **シーン**: PR の度に Kiro に手動でレビュー依頼している現状 → Kiro CLI Headless モードの発見 → CI/CD（GitHub Actions等）への組み込み → spec準拠の自動チェック → リリース前の最終チェック自動化、監査ログ整備（インシデントの続編的扱い）
- **扱う技術**: Kiro CLI Headless モード（KIRO_API_KEY、API key管理）、CI/CD パイプライン統合、spec準拠の自動検証、監査ログ・改ざん検知の自動化
- **感情**: 疲労 → 発見 → 快適さ
- **神谷関係**: 神谷が「リリース判断」、田中が「実装＋自動化」、役割分担が確立
- **コラム候補**: 「Headless モードの安全運用 ── API キー管理とサンドボックス」
- **読者の痛み**: CI/CD 整備したいが何をすればいいか分からない、リリース前検証が手作業

### 第8章：「本番リリース、そして次へ」── 動いて、説明できて、生き続けるプロダクト
- **テーマ**: 完成のその先、Specs文書が生き続ける運用へ
- **シーン**: 本番リリース当日、自治体への正式提供 → 議会・住民説明への神谷の対応、田中も同席 → SLA達成、運用開始の初週 → 田中の振り返り（「ChatGPT 貼り付けの頃と、何が変わったか」）→ 次のカテゴリ拡張への含み → エピローグ（佐藤先輩との偶然の再会、シリーズ世界観への接続）
- **扱う技術**: 本番運用の監視、SLA・KPI 達成、仕様文書の継続更新、「次の Specs」を始めるとは
- **感情**: 達成感 → 静かな自信 → 次への期待
- **神谷関係**: 同期から、深い信頼関係を結んだパートナーへ
- **コラム候補**: 「Kiro のサブスクリプション設計と企業導入判断」
- **読者の痛み**: リリース後の運用が不安、次のプロダクトへの応用が分からない

### ボリューム見積もり
各章 6,500〜9,500字 × 8章 = **合計 56,000〜76,000字**。既刊シリーズ平均レンジに収まる。

### 論点配置の確認
- **論点I（2025-12 Kiro/AWS Cost Explorerインシデント）**: 第5章（Hooks）でメイン扱い、第7章（Headless CI/CD）で副次的言及。「自動化の力」と「自動化の責任」を二段階で描く。原因は「Hook権限」ではなく「エージェント自律判断＋人間承認バイパス」
- **論点D（田中の課題）**: 全章に分散。第1章「動けばいい」の自己認識 → 第2章「言葉にする」苦手の気づき → 第3章「頭の中で済ます」癖の自覚 → 第4〜7章「仕組み化」の価値体感 → 第8章成長の総括
